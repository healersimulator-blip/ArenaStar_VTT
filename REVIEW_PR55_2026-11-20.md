**Verdict: changes required in a follow-up.** The PR is a substantial, well-tested increment:
it closes all three findings from the PR #54 review, adds a genuinely useful marker-changeset
wire format, and documents its capacity limits honestly. However, the new **GM unit-grant control
is not durable**: reconstructing grants from PostgreSQL after a restart silently removes every
other commander's units, and an explicitly empty allowlist silently becomes full control. Two
advertised features — recoverable invites and fixed battle art — are also not functional in the
shipped build. These are functional/authorization regressions in the PR's own headline feature,
not missing scope.

  TypeScript / Vite, single-file build with a 6 MB raw budget). The GM tab is the authoritative

## Findings

### 1. [P1] Unit grants are reconstructed incorrectly — one seat's edit disables every other seat after restart

**Location:** `services/strategic-room/src/postgres.ts:754–772` (`control()`),
`postgres.ts:471–479` (`member.update`), `battle.ts:100–107`, `battle.ts:216–236`,
`authority.ts:106–109`, `schema.sql:43–52`.

`strategic_control` stores only *grant rows*, and `member.update` replaces them with
`DELETE … WHERE member_id=$2` followed by inserts for the new allowlist. There is no row that
records "this seat is unrestricted" or "this seat was explicitly given no units". `control()`
guesses:

```ts
if (!rows.length) return {};                       // "no commander has been restricted yet"
const control = Object.fromEntries(members.rows.map((row) => [row.id, [] as string[]]));
for (const row of rows) control[row.memberId] = row.units;
```

As soon as **any** seat has a grant row, every *other* active player is initialized to `[]`.
`BattleView` treats `state.control[id]` as authoritative, so `own()` returns no units and
`validate()` refuses every order for those seats. `StrategicAuthority.open()` rebuilds the live
view from `db.version(room.version)` on every service restart / campaign `attach()`; `frozen()`
also calls `version()`. Live operation hides the bug because `authority.resolve()`'s
`db.version(result.state.version)` lookup targets an uncommitted version and falls back to the
in-memory `this.control`.

Two failures follow:

| Durable state | `roster()` says | `control()` returns | `BattleView` after restart |
|---|---|---|---|
| fresh room, no grants | all deployments | `{}` | all deployments ✔ |
| GM restricts commander-1 to 1 unit | c1: 1 unit; others: full | `{c1:[…], c2:[], c3:[]…}` | **c2…c500 get zero units** ✘ |
| GM restricts commander-1 to `[]` | c1: full deployment ✘ | `{}` | **c1 regains full control** ✘ |

**Evidence.** I ran the exact `roster()` and `control()` SQL against an embedded PostgreSQL
(PGlite) with three 5-unit seats, and fed the reconstructed `control` map into the production
`BattleView` in a temporary vitest probe:

```
--- B. GM restricts commander-1 to one unit ---
roster commander-2: units=["unit-2-1" … "unit-2-5"]   (GM sees full control)
control(): {"commander-1":["unit-1-1"],"commander-2":[],"commander-3":[]}
BattleView commander-2: [] / commander-3: []           (authority sees none)

--- C. GM restricts commander-1 to an EMPTY allowlist ---
roster commander-1: units=["unit-1-1" … "unit-1-5"]   (GM sees all boxes checked)
control(): {}
BattleView commander-1: ["unit-1-1" … "unit-1-5"]     (ban silently undone)
```

The `BattleView` probe (2 assertions) passed, confirming `own()` follows `state.control`
exactly as described. In the validation continuation I also reproduced both failure cases
end-to-end against a real PostgreSQL 18.7 wire service and a freshly opened
`StrategicAuthority`: after restricting one seat, commanders 2/3 had zero units, `roster()`
still reported five units each, and an order from commander-2 was rejected with
`invalid_order`; after an empty allowlist, commander-1 regained all five units. That temporary
DB probe was removed. Note also that `strategic_versions` has **no `control` column**
(`schema.sql:43–52`): `Published.control` is computed from *current* grant rows at read time.
The comment "Unit grants are part of a publication, not a live overlay: a view always states its
own grants" is not implemented; historical versions inherit today's grants.

`roster()` (`postgres.ts:273–290`) has the mirror-image bug: it uses
`coalesce(array_agg(grant rows), deployment)`, so an empty allowlist (zero rows → `array_agg`
returns `NULL`) is reported as the whole deployment. `MemberRow.units` is documented in
`protocol.ts:142` as "an empty list means visibly no control". The GM UI and the authority
therefore disagree in both directions, and a GM cannot restore a no-unit state from the roster:
clicking one checked box sends a list containing all the other units, re-granting them.

**Impact.** A routine GM action on one seat breaks the other 499 seats after any restart, and a
"no units" restriction is silently revoked. This defeats the PR's central claim that unit rights
are enforced in the authority, and its restart/resume claims. `tests/strategicRoom/postgres.test.ts:139–226`
only checks the *changed* seat; `edge.test.ts` only sets a non-empty allowlist. No test restricts
one seat and then reopens the authority.

**Fix.** Persist an explicit per-seat grant mode at room creation (e.g. one row per commander
with `mode: 'deployment' | 'allowlist'` and the allowlist), so "unrestricted", "some units" and
"no units" are all representable. Make `roster()` and `control()` read that single source, and
store the resolved control map with each publication (or version-keyed) instead of recomputing
it from live rows. Add regression tests: restrict one seat → reopen → all other seats keep their
deployment; restrict a seat to `[]` → reopen → still `[]`; a later grant edit must not change an
older version's view.

### 2. [P2] Campaign invite recovery returns invalid codes for reissued invites; the code is lost on reload

**Location:** `src/ui/strategicRoom/HostedRoster.svelte:70–74`,
`services/strategic-room/src/postgres.ts:542–560`, `campaign.ts:207–236`,
`services/strategic-room/README.md:119`.

`HostedRoster.invite()` generates `crypto.randomUUID().replace(/-/g,"")`, stores it in
component-local `$state`, and sends `member.invite`. The server stores **only its SHA-256
digest**; no command or endpoint returns the plaintext. If the GM reloads (or the iframe
remounts), `invites` is gone; `roster()` reports `invite: "reissued"` and the UI shows
"invite already issued" with **no reissue button** (`HostedRoster.svelte:148`). That seat is
unclaimable until the 30-minute expiry.

Worse, `serveCampaign`'s launch/retry endpoint derives codes for *all* seats that currently
have an `invite_hash` from `HMAC(launchKey, [id, member])`:

```ts
const ids = … WHERE invite_hash IS NOT NULL AND invite_expires>now() …
return json(res, 200, { id, invites: Object.fromEntries(ids.map((i) => [i, invite(i)])) });
```

That HMAC code is correct only for the invites minted at `create()`. For a seat reissued through
the roster, the stored hash is `digest(randomCode)`, so `admit()` compares a different digest
and refuses. **"Recover invites / retry launch" returns a code that cannot join that seat.**

**Evidence.** Direct crypto check with the exact functions:

```
stored invite_hash (reissue)  : de4147fa…3c8    = sha256(randomUUID hex)
retry launch returns HMAC code : 68Z6bRX2BJkgMn3C1XGd-cMqKYl0K_AGy0owGYKhK9M
digest(HMAC code)             : 90b1d69c…5a
would admit() match?          : false
```

`e2e/campaign_battle.spec.ts:80–128` exercises retry launch only with the original HMAC invites
(immediately after launch), so the reissue path is untested.

**Fix.** Make reissued invites recoverable from the same authority: either have the server mint
and return the code (storing only a short-lived resend-safe copy with GM-bearer-only access), or
derive every invite — including `member.invite` — from the same KDF and verify the digest matches
before listing a seat as recoverable. Show the code only after the matching accepted receipt.
Add an e2e case: let the initial invite expire → reissue from the roster → retry launch → a
commander joins with the returned code.

### 3. [P2] "Fixed battle art" is inert in the shipped build, and the endpoint cannot be reached by a browser

**Location:** `server.ts:147–165` (`mediaAssets`), `server.ts:188–192`, `server.ts:512–545`,
`server.ts:650–657`, `PROTOCOL.md:1795`, `services/strategic-room/build.mjs`.

- `mediaAssets()` reads `../web/scene/*.webp`. **Nothing creates that directory**: `build.mjs`
  only builds the server and `web/`; there are no `.webp` files under
  `services/strategic-room/`, and `corepack pnpm build:strategic` produced `dist/web/` with
  `index.html` + `assets/` and **no `scene/` directory**. So `media` and `mediaByHash` are always
  empty; every hash is a 404, including valid ones.
- The endpoint requires `req.headers.origin` to be present and in `origins`
  (`server.ts:523–527`). Browsers do **not** send `Origin` on a same-origin GET (an `<img>` or a
  `fetch`), and `Origin` is a forbidden request header that script cannot set. A Node `fetch`
  probe confirmed `origin: null` for same-origin GET with and without `mode: "cors"`. Even if art
  were shipped, the success branch would be unreachable from the deployed UI; a foreign `Origin`
  is already 404. The inner `sceneMedia()` origin check is redundant.
- No client consumes `Baseline.media` / `StoreMedia`: searching `src/ui/strategicRoom`,
  `src/client` and `src/app` finds no reference to the field or to `scene/<hash>.webp`.
- The tests only assert **404**: `tests/strategicRoom/edge.test.ts:280–297` (unknown hash,
  foreign origin, malformed path) and `e2e/hosted_strategic.spec.ts:441`. There is no 200 case,
  no real asset, and no browser consumer — yet `PROTOCOL.md:1795` and the PR body describe it
  as delivered, same-origin, immutable, content-addressed battle art.

**Fix.** Either ship the art in `build:strategic`, serve it to an admitted GM session (bearer /
`Sec-Fetch-Site`, not an `Origin` header browsers omit), wire `media` into an actual client
fetch, and add a 200 + cache-behaviour test; or remove the dead endpoint, the `media` metadata
field and the doc/PR claim. As merged, the GM view advertises an empty list and the feature does
nothing.

### 4. [P2] Scene-pack reader's 512 MiB bound does not cover unlisted entries (zip-bomb / OOM)

**Location:** `src/client/scenePack.ts:46–89`, `src/core/scenePreload.ts:30`,
`src/app/JoinApp.svelte:689–715`.

`readScenePack` checks only the **compressed** archive size, then calls `unzipSync(bytes)`,
which eagerly inflates *every* entry before any validation. The uncompressed accounting is
`total += data.byteLength` **only for entries whose hash is in the manifest** (line 78);
unlisted entries `continue` at line 73 first. The post-hoc `names.length >
MAX_PACK_ASSETS*2+1` check caps entry *count* (4097), not bytes, and happens after inflation.

A tiny zip bomb with a handful of highly compressible, unlisted `assets/…` entries can therefore
decompress well past `MAX_PACK_BYTES` (512 MiB) with no error. The pack is explicitly described
as untrusted ("an invite peer or a shared file"), and a player imports it before connecting.

**Evidence.** A temporary vitest probe with `unzipSync` stubbed (to avoid allocating 600 MiB in
this sandbox) returned `{ rejected: 1 }` with **no throw** for a single unlisted 600 MiB entry —
the reader never applied its own cap. Also `parseScenePackManifest` never checks
`entry.size` against the actual byte length, and `AssetCache.put` stores the pack-supplied MIME.

**Fix.** Bound total inflated bytes across **all** entries (including rejected/unlisted ones),
prefer a streaming/incremental unzip or read the zip central-directory uncompressed sizes before
inflating, cap per-entry size, and verify `data.byteLength === entry.size`. Add a zip-bomb test
with a small compressed fixture.

### 5. [P3] Documented roster-generation and revoke semantics are not implemented

**Location:** `postgres.ts:542–560`, `postgres.ts:507–528`, `PROTOCOL.md:1792`,
`services/strategic-room/README.md:120`.

- Both docs state "**Each accepted command bumps the roster generation**" / "Every accepted
  roster or control command bumps the head's `members` generation". `member.invite` returns
  `finish({ receipt, invites })` with **no `room`**, so `authority.submit` never calls
  `changed()` and no head is pushed. The GM roster's `invite` flag can be stale in another tab,
  and the documented refetch contract is violated. (`member.update`, `kick`, `revoke` do call
  `setMembers`.)
- `PROTOCOL.md:1792` says `member.revoke` "drops its grants and orders". The SQL only sets
  `active=false`, clears the invite fields and deletes `strategic_orders`;
  `strategic_control` rows survive and `control()` re-injects them for the inactive id
  (`postgres.ts:776`). Functionally harmless because the seat is inactive, but the durable
  state does not match the contract and shows up in exported views.

**Fix.** Implement as documented (bump on invite; delete control rows on revoke) or correct the
docs/tests to describe the actual behavior. Add explicit assertions.

### 6. [P3] Smaller issues worth a follow-up

- **Invite code shown before acceptance.** `HostedRoster.svelte:70–74` writes the code into
  `invites` and renders it before the command result; `onCommand` discards
  `client.submit()`'s boolean. A refused command (claimed-seat race, `busy`, disconnected) still
  displays a code that can never admit. Gate display on the matching accepted receipt.
- **`BulkReads.enter()` can starve waiters.** `bulkReads.ts:23` grants a slot whenever
  `active < limit` without consulting `queue`; `server.http` calls `bulk.enter()` directly, so a
  fresh request can jump ahead of sessions waiting in `bulk.wait()` during a publication burst.
  Serve the queue first.
- **A single global `members` generation invalidates all 500 views.** Any one-seat edit pushes
  a head to every session. Those same-version refetches request `STRATEGIC_VIEW_TYPE`, which is
  **not** eligible for `BulkReads.wait()` (`server.ts:570–585`), so they meet 429 and retry in
  waves. Per-member generations, or making metadata-only refetches wait-eligible, would avoid
  needless load on the exact 500-seat scale this PR targets.

  `tests/strategicRoom/edge.test.ts` and `postgres.test.ts`; GM-only roster redaction, the 4001
  kick frame and same-key resume are all real edge tests.
- The marker-changeset format is carefully specified in `PROTOCOL.md` and defensively decoded
  (`viewWire.ts:applyMarkerChanges`): epoch/version/role/faction checks, strict index ordering,
  run-length and coordinate validation, and graceful fallback to a full view.
  `tests/strategicRoom/viewWire.test.ts` covers corrupt frames, 500-seat metadata and 50k
  markers. `BulkReads` is bounded and has unit tests.
- Scene preload's *policy* half is sound: `sceneMediaIds` uses the player projection, omits
  GM-private / export-restricted media, drops GM provenance, and `readScenePack` verifies every
  accepted byte against its path hash before caching. The defect above is only the missing
  decompression bound.
- The host-side write fence (`sync.ts`, `campaignScene.ts`, `turnChannel.ts`) blocks direct
  binding edits and local strategic simulation while a battle is live, allows scene navigation,
  and refuses to inherit a binding into a copied world. `battleBlocks` tests cover embedded ops.
- Documentation is unusually thorough and the capacity claims are consistently caveated
  ("500 seats is a configuration limit, not verified capacity"). The new
  `docs/STRATEGIC_MECHANICS_TEST_REPORT.md` clearly separates historical expected failures
  from the fixed behaviours.
