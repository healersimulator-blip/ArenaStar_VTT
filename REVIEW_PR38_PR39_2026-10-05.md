## 1. PR #38 — the plan document

**Verdict: strong, and unusually honest.** It is the kind of pre-implementation document this repo
already uses well (`GAP_CLOSURE_ImplementationPlan.md`, `WorldFile_Packaging_Proposal.md`).

What it gets right:

- **It separates undoability from rules execution.** The core finding — *"no producer ever puts a
  condition/effect op into an envelope that a revert mechanism owns"*, i.e. conditions are not
  un-revertible because Revert is field-limited, but because nothing hands Revert a condition — is
  correct against the code it describes.
- **It maps every producer before proposing a fix** (§3): trip/overrun, Dirty Trick, grapple family,
  Dying/Stable, first aid, spells, poison, bull rush/trample, with the seams each touches.
- **It records the gaps it could have hidden**: **G-A8** (afflictions have no model), **G-A9**
  (legacy condition *names* are not mechanically resolved — a claim it later had to make good on),
  **G-A10** (no application identity/source lifecycle), **G-A11** (the F01 `RollLedger` puts raw
  `ledgerOps`/`ledgerInverses` on a **public** message, and the receipt hashes the whole message so
  ledger pruning would stale it). G-A11 is still true at HEAD (`src/core/projection.ts` has no
  `rollLedger` handling), so the plan's own gate on Phase 3 is live, not theoretical.
- **R1–R7 are real decisions with consequences**, not preferences: R1 private receipt as the single
  inverse store; R2 per-path staleness for keyed records; R3 refuse-and-report rather than time-travel;
  R4 a *separate* keyed `conditionApplications` map instead of widening `conditions: string[]`;
  R5 one exposure/tick per audited event; R7 Core-rules poison with explicit cure wording and
  round-down.
- **Phase bodies carry acceptance tests and interlocks** ("Phase 1 precedes every new condition
  writer", "Phase 6 depends on Phases 1, 2 and 4"), and §5 non-goals are explicit (no player-facing
  Revert, no arbitrary branching, no Unchained tracks).

Weaknesses:

1. **Phase 0 was left incomplete by its own definition.** §4 Phase 0 lists five characterization
   items — (a) legacy Home-A labels vs effect-derived mechanics, (b) Pinned escape, (c) Deafened's
   absence, (d) public `rollLedger` projection, (e) receipt staleness after ledger update/prune — and
   says *"Remaining before production work: decide R1–R7 and add characterization for (a)–(e)"*. The
   merged test file contains **4** tests and none of (a)–(e) as such; production work then started
   anyway. (e) in particular guards the Phase 3 design.
2. **Phase 2 is too large to be one slice** — "replace the two-submit maneuver path… route trip/overrun,
   Dirty Trick, all grapple branches, Dying/Stable, first aid and manual apply/edit/remove…" spans five
   call sites, the action ledger, receipts and e2e. The implementation predictably delivered only the
   manual slice (§2.4 below). Recommend splitting it into 2a/2b/2c with separate acceptance.
3. **The plan is silent on two questions the implementation had to answer**, and chose without
   recording: (i) *who rolls the saving throw* — §4/§6 says the host "re-reads… validates the
   roller/commit-reveal result", while the code host-rolls with `cryptoRng` (see §3); (ii) *whether a
   condition change is announced* — PF1e at a real table, a condition is visible table state, but the
   manual path produces no chat entry at all.
4. **Decision-record hygiene.** `PLAN.md` states the project convention: "judgement calls in
   `DECISIONS.md`". R1–R7, and specifically R4 (a persisted-document contract change), were recorded
   only inside the plan; `DECISIONS.md` has **zero** mentions of condition applications or poison and
   its last entry is still D-405.

**Rules soundness of the plan itself: good.** Its §6/§4 poison text reproduces the FAQ's rules
accurately (I checked each numbered point in §7.3), names the deliberate choices (round-down of a
fractional half-duration, disease ≠ poison, no timed Prone), and cites CRB pages rather than memory.
The one earlier rules error — the timed-Prone proposal — was removed in this revision.

## 2. PR #39 — the implementation

### 2.1 What is genuinely good

**Condition applications (Phase 1) are well built.**

- `conditionApplications.ts` is id-keyed, source-aware (`kind/id/actionId/actorId/itemId/abilityId/
  relationshipId/groupId`), removal-policy-carrying, bounded (256 entries, 1–128-char ids), validated
  through the actor parser, and **read-compatible with the legacy array without rewriting old worlds**
  (`readPF1eConditionApplications` synthesizes permanent source-unknown views for legacy strings).
- **G-A9 is actually closed.** `resolvePF1eConditionEffects` merges supported applications *and legacy
  names* through `def.build()` into the normal effect pipeline, deduplicated by condition name, with
  Pinned suppressing Grappled mechanics **and** the mirrored name — so a maneuver's legacy `"Prone"`
  write now mechanically denies ranged attacks and applies −4 melee in `actionRefusal`
  (`actions.ts:519-537`, including the pinned-escape and prone-crossbow exceptions). This is the single
  most valuable change in the PR, and it fixes pre-existing behavior, not just new code.
- Immunity refusals (`conditionRefusalFor`) are wired on the typed apply path; unsupported labels are
  preserved and *reported*, never silently given mechanics.

**The poison engine (Phase 6) is a faithful CRB + FAQ implementation.** I verified the math against the
FAQ text point by point (§7.3): dose-adjusted exposure DC `base + 2·max(0, n+m−1)` and ongoing DC
`base + 2·(n−1)`; extension `floor(base/2)` intervals **per additional dose** applied from the current
course end (never restarting or shortening); effect on every failed save including failed re-exposures;
one save for a simultaneous ingested/inhaled batch at the higher DC; cure `successesRequired` with the
`consecutive` flag preserved per entry (Greenblood 1 save / Octopus "2 saves" / Wyvern "2 consecutive
saves"); a failed save against the same identity resetting a consecutive streak only; distinct
identities tracked separately; HP/ability damage never healed on cure; immunity; per-attempt
idempotency; damage-free "no onset, no frequency" one-shots; onset suppressing effects until its
boundary; `delay poison` pausing without backfilled saves and queueing new exposures in timestamp order;
`neutralize poison` ending one course exactly. The three shipped real-world profiles are transcribed
correctly (Octopus DC 19 / 1 round ×6 / 1d3 Str / cure 2 saves; Wyvern DC 17 / 1 round ×6 / 1d4 Con /
cure 2 **consecutive** saves; Greenblood DC 13 / 1 round ×4 / 1 Con / cure 1 save — §7.2).

**Authority and reversal are handled the way the repo demands.** Dose count, DCs, save results, course
state, effect Ops and receipt identity are all host-derived; `system.pf1e.afflictions` is completely
host-owned (any generic client op that changes it is refused); conditions may not be *mutated* by
generic ops; exposure is GM-only and `frequency` cannot be client-authored at all — and `PROTOCOL.md`
documents exactly that, including the reason. Revert reuses the existing private `actionReceipts` with
a new **path-scoped** post-image mode (`documents.ts` `hashMode:"paths"` / `pathHashes`), which is the
right answer to R2: a sibling poison course, or an unrelated HP edit, no longer stales a receipt. The
tests prove that (`pf1ePoison` "Revert of one poison tick preserves a sibling course";
`pf1eConditionAction` "Revert preserves unrelated HP", "a later edit to the same application makes its
original Revert stale").

**Protocol plumbing is correct.** `pf1e.poison` 0x53, `pf1e.condition` 0x54/0x55 — I checked all 67
`MsgKind` values for collisions: none. Frame codec, fixtures, client API, PROTOCOL sections and the
protocol-doc consistency test are all updated.

### 2.2 Defects and gaps

**D1 (High, rules) — `Panicked` forbids the escape casting the rules require.**
`conditions.ts:346-353` denies `standard`, `swift`, `full-round`, `five-foot-step`, both attacks and
`cast-spell`. CRB p.565: *"A panicked creature can use special abilities, including spells, to flee;
indeed, the creature must use such means if they are the only way to escape."* The library blocks
exactly that escape hatch and its `notes` do not record the restriction as intentional. (Compare
`Frightened`, which does not deny anything and notes flee as caller-owned.)

**D2 (High, integration) — poison has no producer anywhere in the app.** `requestPF1ePoisonAction` is
called only from `tests/host/pf1ePoison.test.ts`; the only "poison" strings in `src/ui` are an
unrelated hexcrawl comment and `"poison"` as an effect-source label in the effect editor. There is no
sheet control, no GM expose dialog, no course/DC/due readout, no attack hook, and no
`e2e/pf1e_poison.spec.ts` — which the plan's own Phase 6 acceptance *requires*. So the engine is
reachable in play only by a GM writing wire messages: Phase 6 is implemented, not usable.

**D3 (Medium-High, integration) — the D-405 Action System is bypassed.** Plan Phase 2 says the host
"normalizes the D-405 action record" and commits "in one `commitOps` envelope". Instead poison events
write a **plain chat message** (`system.pf1ePoison`, `sync.ts:3563-3584`) and condition actions write
**no message at all** — only the actor op and a private `pf1e.condition.result` to the requester. No
`ActionCard`, no `ActionFxContext`, no card-level Revert (Phase 3 is still open, so that part is
expected), but also a second, third and fourth card vocabulary in chat next to `system.action`. This is
the main architectural misalignment of the PR: the repo now has two parallel "durable fact" forms.

**D4 (Medium, security/consistency) — the host's generic-op guard is not closed.**
`sync.ts:2743` refuses changes to existing `conditionApplications` and `sync.ts:2756` refuses
non-manual sources — but a client op that **adds** an application self-attributed as
`source.kind:"manual"` with `source.id === user.id` and `removal.kind:"manual"` is **accepted**. That
writer skips `conditionRefusalFor` (immunity) and gets no receipt — the two properties the typed path
exists to provide — and it contradicts both the neighbouring error text and the plan's claim that
"generic client Ops directly mutating condition applications… are rejected". No in-repo producer needs
this allowance (`pf1eApplyConditionApplication` is only called from the two host paths), so it should
either be removed or routed through the same validation.

**D5 (Medium, rules) — Deafened's −4 on opposed Perception checks was not added.**
`stealthPerception.ts:256` applies the opposed-check penalty for `blinded` only; the PR added
`requiresHearing` auto-fail for deafened (line 371) but not the −4. Plan Phase 1 names "sound-based
Perception, **opposed Perception** and verbal spell-failure consequences" explicitly, and the new test
only asserts Blinded's −4. (Initiative −4 and the 20 % verbal spoilage *are* wired — the latter in
`pf1eCastFlow.ts:963-983`.)

**D6 (Medium, rules/annotation) — the skill-check penalties of the fear/sickened family are missing
while the notes claim they are impossible.** `Shaken`, `Sickened`, `Frightened` and `Panicked` each
carry a note that skill/ability-check penalties have "no mod keys — caller-owned". That is no longer
true: `PF1E_MOD_KEYS` contains `skills` and the whole `skill.<id>` family, and `derivePF1eSkill`
(line 188-191) reads `skills` + `skill.<id>` + legacy keys. Only the *ability-check* half of the
statement is accurate. Either add `mod("skills", −2, …)` (and the sight/hearing-specific ones where the
consumer owns them) or correct the note.

**D7 (Low-Medium, trap) — `removal: {kind:"expiry"}` is validated but consumed by nothing.** Validation
accepts a full expiry policy (`value/unit/boundary/appliedAt/expiresAt`), and no code anywhere reads it
(this was Phase 4's job). Nothing sets it today, but the schema now promises a behaviour the engine does
not have; until Phase 4 lands, the applier should refuse (or loudly warn on) an `expiry` removal.

**D8 (Low, redundancy) — poison-owned conditions are tracked twice.** `poisonEffectPlan` writes
`removal: {kind:"event", event:"poison-cured"}` *and* records the id in `course.activeEffectIds`; only
the latter is read (`poisonRemoveEffectOps` → `pf1eRemoveConditionApplication`). Two bookkeeping
channels for one fact is exactly the "do not duplicate state" pattern the plan warns about.

**D9 (Low, architecture) — the poison catalogue is code, not data.** `PF1E_POISON_FIXTURES` is a
hard-coded array in `afflictions.ts`; the host looks definitions up by id in that array. The repo's own
rule (`PF1e_Unified_TODO` §0 rule 4, and `systems/pf1e-core` being data-only) and the plan's own "6a.
Immutable poison definition (source data)" point the other way: a content pack should be able to ship
poisons. Related: `bestiary.json` contains **0** occurrences of "poison", `statBlock.ts` has no poison
handling, and no fixture exercises the otherwise-implemented `dcSource:"creature-derived"` path, so
that branch is currently unreachable.

**D10 (Low-Medium, plan fidelity) — Phase 2's producer set is untouched.** Trip/overrun, Dirty Trick,
the grapple family, Dying/Stable and first aid still write the legacy array with client-submitted ops
and no receipt (`pf1eManeuver.ts` `conditionOps`/`conditionSetOps`, `pf1eDyingTick.ts:48`,
`pf1eFirstAid.ts`), so none of them is named-Revertable — the plan's Phase 2 acceptance ("GM Revert
restores the exact prior mechanical state for a trip, Dirty Trick, initial grapple/pin/escape, and
first-aid/dying") is unmet, and the PR header's "**Phase 2 & Phase 6:** Landed…" reads as more than
what shipped.

**D11 (Verification) — the PR merged with the gates red.**
- `pnpm lint` fails with **9 errors, all in PR #39's new code**: `src/host/sync.ts:3917,3918,3919,3920`
  (`no-useless-assignment` ×3, `prefer-const`), `:4184`, `:4205` (`prefer-const`);
  `src/packages/pf1e/conditionApplications.ts:368` (`no-dynamic-delete`);
  `tests/packages/pf1eAffliction.test.ts:274,310` (non-null assertion, `prefer-const`).
- No e2e was run for the new surface (no spec exists), and the canonicalization of the derived
  condition list broke an existing one: `e2e/pf1e_concentration.spec.ts:106` expects the lowercase
  legacy label `"deafened"` and now receives the canonical `"Deafened"`. In-app consumers all compare
  case-insensitively, so this is a stale expectation — but it is red at HEAD and directly caused by
  this PR. (The other 18 reproducible e2e failures at HEAD — the `casts X` ActionCard prose,
  reaction prompts, held charges, hotbar slots, hexcrawl travel hint, movement end-square — are *not*
  attributable to this PR on the evidence I have; several belong to the earlier D-405 card rewrite.)
- `pnpm typecheck` (0 blocking), `pnpm test` (4,993 passed / 12 skipped) and `pnpm build`/`size`
  (4.31 MB raw) do pass on this tree.

## 3. Is the plan sound?

**Structurally: yes.** The dependency order (state → mechanics → host transaction → card UX →
scheduler → spells → poison → movement → surfaces) is the right one, the interlocks are stated, the
non-goals are enumerated, and the acceptance criteria are test-shaped rather than aspirational. It also
does something rare: it names the *reasons a naive implementation would fail* (a reversible label is
not a mechanic; a public ledger is not a private receipt; a timer is not a duration rule).

**But the plan and the code have now diverged in ways the document no longer reflects:**

1. **Sequencing was skipped, not documented.** Phase 6 was implemented before Phase 4, and it built its
   own scheduler instead of the shared one the plan demanded ("if the present combat model cannot
   represent the required initiative boundary, decide and document that limitation *before* adding the
   timer"). The poison cadence does honour the FAQ's turn rule, so this is defensible engineering — but
   the general expiry contract is still unimplemented (D7), so the plan's "one scheduler" invariant is
   now false in the code.
2. **Phase 2's headline scope didn't shrink in the document** when only its manual slice shipped (D10).
   The header status reads "Phase 1 / Phase 2 & Phase 6 landed" with no "what remains" list inside the
   phase bodies, which is the exact failure mode the same repo called out in its own 2026-09-21 status
   assessment ("gap-document drift"). Re-sync the phase bodies the way `GAP_ANALYSIS` was re-synced.
3. **Two implementation-level decisions are missing from the plan**, and one of them is a rules decision
   the plan should own: host-rolled vs player-rolled saves, and whether these events are D-405 action
   cards (D3). Both change the *contract*, not just the code.
4. **Acceptance is not yet dischargeable as written**: Phase 6's list includes e2e and race/rollback
   cases; the e2e is absent and "combat/world-clock race cases" are not clearly covered.
5. **Process rule**: R1–R7 and the persisted-contract change belong in `DECISIONS.md` under the repo's
   own convention; they are only in the plan today.

**Does the plan conform to PF1e?** Its rules content does, and its cited deviations are deliberate,
named and minimal (round-down of `floor(baseDuration/2)`, onset semantics, disease ≠ poison, no timed
Prone). The two rules defects found in the shipped library (D1, D5) are *implementation* gaps relative
to the plan's own Phase 1 text, not plan errors.

## 5. What I would do next, in order

1. **Green the gates.** Fix the 9 lint errors; update `e2e/pf1e_concentration.spec.ts:106` (or keep
   and assert the canonical name); add the plan-required `e2e/pf1e_poison.spec.ts` plus a conditions
   spec so the new host paths are browser-verified.
2. **Fix the two rules defects** (D1 Panicked escape casting; D5 Deafened's −4 opposed Perception) and
   correct or implement the skill-penalty notes (D6).
3. **Give poison a producer and a surface** (D2): an "apply poison" action from an attack/weapon card,
   a course panel (state, doses, DC, next save, cure progress, Revert hook), and a GM expose dialog.
4. **Move definitions to `systems/pf1e-core/packs/afflictions.json`** with the four fixtures plus
   creature-derived DCs sourced from the bestiary's HD/Con (D9), so content ships as data and the pack
   boundary holds.
5. **Decide and write down two contracts** (D3, and §3.3): action card vs plain message; host-rolled vs
   player-rolled saves (commit-reveal). If action cards are adopted, condition/poison events inherit
   FX, chat rendering and Phase 3's card Revert for free.
6. **Close the generic-op allowance** (D4) so the typed path is the only writer, or run it through the
   same immunity/receipt validation.
7. **Resolve the `expiry` trap** (D7): refuse it until Phase 4, or land Phase 4's consumer.
8. **Re-sync the documents** (D10, §3.2, §3.5): annotate each phase body landed/partial/remaining,
   split Phase 2, and record R1–R7 plus the R4 persisted-contract change in `DECISIONS.md`.

**Bottom line.** PR #38 is a good plan and PR #39 is a good engine: the rules math is a faithful
transcription of CRB + the poison FAQ, the condition-instance design is right, and the path-scoped
receipt is a genuinely better answer than the plan asked for. What is missing is the *last mile*: the
poison engine has no producer or UI, the action-card contract wasn't adopted, two conditions diverge
from the printed rules, the persisted schema promises an expiry nothing enforces, and the PR merged
with lint red and no browser coverage. None of that is a redesign — it is Phase 2b/3/4/5/8 work the
plan already anticipates, plus a short cleanup list.

## 7. Sources checked for the rules claims

1. **Conditions** — Archives of Nethys, CRB p.565 (<https://www.aonprd.com/Rules.aspx?ID=413>):
   Panicked ("can use special abilities, including spells, to flee"), Deafened ("–4 penalty on opposed
   Perception checks"), Blinded, Grappled, Pinned ("denied its Dexterity bonus… additional –4 penalty
   to his Armor Class"), Prone, Shaken/Sickened, Staggered/Stunned/Unconscious, Helpless (Dex 0).
2. **Bestiary stat blocks** — Giant Octopus, Bestiary p.219 (<https://www.aonprd.com/MonsterDisplay.aspx?ItemName=Giant%20Octopus>):
   "save Fort DC 19; frequency 1/round for 6 rounds; effect 1d3 Str; cure 2 saves"; Wyvern, Bestiary
   p.282 (<https://www.aonprd.com/MonsterDisplay.aspx?ItemName=Wyvern>): "save DC 17; frequency 1/round
   for 6 rounds; effect 1d4 Constitution damage; cure 2 consecutive saves".
3. **Poison FAQ** — Paizo, "I Drank What? An FAQ on Poison" (<https://paizo.com/blog/i-drank-what-an-faq-on-poison>):
   points 1–7 (exposure save; +2 DC per active dose; saves on the creature's turn and not delayed;
   effect on every failed save; duration +½ only on a failed *initial* save; one save for simultaneous
   inhaled/ingested batches; similar-but-different entries tracked separately) and the three Greenblood
   scenarios, including "three active spider doses ⇒ DC 18 / eight rounds" used by the unit fixture.
