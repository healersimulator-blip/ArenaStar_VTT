## Implementation follow-up — 2026-10-02 (TR-01/A19 per-viewer scene load)

`sceneLoad` is now a host-dispatched method for the per-viewer half of MATT's scene trigger. MATT has a single `canvasready` mode (UI label "Scene Change") that, per its wiki, "runs the tile actions when the scene is loaded by a player … it will trigger for each player loading in"; this engine keeps the two moments distinguishable instead of fused: `sceneChange` is the committed activation transition (once per commit, D-376) and `sceneLoad` is **a viewer loading the active scene it does not already hold**. They never coincide, so a graph may subscribe to both without double-firing, and each has its own history entry.

The host remembers what each user last loaded (`loadedSceneByUser`): a session completing its join — GM loopback or approved player — fires `sceneLoad` for the active scene when that differs from the remembered one; a plain reconnect to the same scene is silent; a viewer who was away while the table moved fires on return, while one who was present for the activation already follows it (their record is updated by the activation) and is silent. With no active scene there is nothing to load. A viewer may join an active scene. Dispatch uses the shared scene-wide loop (descending Sort, stable IDs, live re-validation), carries no triggering token, and fires under that viewer's identity — so a GM-authored graph can react per viewer (`{{user}}` names the viewer) while unpublished graphs stay silent for players and the viewer receives neither the graph definition nor GM-only history. `automation.request`/`automation.fire` refuse the method.

## Implementation follow-up — 2026-10-02 (TR-01/A19 lighting and time changes)

MATT's two environment triggers are now host-dispatched methods, following the same separate-events model as doors and combat: **`lightingChange`** for a committed change to a scene's ambient darkness (MATT's On Lighting Change, its `updateScene`/`darkness` hook) and **`timeChange`** for a committed change to the replicated world clock (MATT's On Time Change, its `updateWorldTime` hook). The wizard labels them "lighting change" / "time change"; routing, method filters and `{{method}}` work unchanged, and neither is offered as a manual simulation — `automation.request` and `automation.fire` accept only `SIMULATABLE_METHODS`, so a client cannot manufacture an environment event, and a player cannot write the clock at all (`forbidden`).

HostSync captures the committed pre-images — a scene's `darkness` for scene updates, and the merged world-clock value for any `settings` write (including the creating envelope that installs a world-settings document, and deletes that revert the key) — then compares after apply, so a real change decides and a same-value write is silent. Dispatch mirrors MATT's scene-wide scope, where doors need midpoint geometry and combat needs the encounter's scene: a lighting change fires every graph anchored in **the changed scene** (active or not, exactly as MATT reads the changed scene's tiles) and a clock change fires every graph in the **active scene** (MATT's time trigger watches the scene the table is looking at, which for the host is what a fresh player loads). Both use the shared ordered anchor loop with live re-validation (descending Sort, stable IDs), carry no triggering token — MATT passes controlled canvas tokens, a client-side selection this engine has no host equivalent for, documented on the dispatch — and share one depth-8 reentry budget because a graph's own Scene Lighting or Game Time action commits another environment change. Undo/Redo/Revert never replay, and the reentry budget bounds a self-retriggering pair instead of growing the host's call stack.

## Implementation follow-up — 2026-10-02 (TR-01/A19 combat changes)

The five combat changes MATT exposes as separate trigger kinds are now distinct host-dispatched methods, named once in `COMBAT_TRIGGER_METHODS` (`src/core/combat.ts`) so the automation contract cannot drift from the classifier: `combatStart` (an encounter starts: round 0 → ≥ 1, or a started document is created — the tracker's Start button creates it at round 1), `combatRound` (the round advances), `combatTurnStart` (a new current combatant begins), `combatTurnEnd` (the combatant whose turn ends, reported from the pre-change state) and `combatEnd` (a running encounter is reset to round 0 or deleted). The wizard labels each ("combat start" … "combat end"); a graph listing several kinds hears each, and none of the five is offered as a manual simulation — `automation.request` and the module `automation.fire` path accept only `SIMULATABLE_METHODS`, so a forged payload cannot manufacture an encounter event.

`combatTriggerEvents(before, after)` is a pure classifier over the committed pre-image and the live document, following the repository's own `startCombat`/`nextTurn`/`previousTurn`/`endCombat` transitions plus MATT's hook semantics: a started encounter appearing begins start → round → turn start; a round advance is turn end → round → turn start; a turn advance is turn end → turn start; stepping back is a turn start only; combatant-only edits, same-value updates and unstarted (round 0) edits are not events. HostSync captures a `combats` pre-image for round/turn/combatant updates, creates and deletes, then fires on the post-commit comparison — never on the presence of a diff key, because the tracker sends both `round` and `turn` on every push. Dispatch mirrors MATT's scene-wide scope (it fires the encounter's own scene's tiles; there is no midpoint/anchor geometry test like doors): every graph anchored in the encounter's scene whose method list contains the event, re-validated live, ordered one authored change at a time and within a change by descending Sort then stable IDs. The encounter's scene resolves from its own `flags.core.sceneId` binding (falling back to the scene whose active-encounter pointer names it). Each event carries the current combatant as the triggering token (`combatTurnEnd` reports the outgoing one); Undo/Redo/Revert never replay a combat event, the dispatch is depth-capped at 8, and host work without a live session synthesizes the system caller like the movement and door paths.

## Implementation follow-up — 2026-10-02 (TR-01/A19 door changes)

Scripts can query/edit tags with Tagger-style `getTags`/`hasTags`/`getByTag` and atomic bulk set/add/remove/toggle/clear helpers, send chat, play/list/stop matching FX, fire published automations, call other scripts and atomically place GM-reviewed prefab IDs via an explicit grant/allowlist. Reviewed Workers additionally expose `api.fx.playAndWait(id)` and a bounded `api.fx.sequence().play(...).parallel(...).playAndWait(...).wait(...).call(...).thenDo(...).run()` builder with ordered results. They await finite host-clock cue windows, not client decoding, and do not provide a global scheduler or an atomic transaction. `api.tags.applyTagRules(refs)` explicitly expands already-authored `{id}`/`{#}` templates in one undoable edit; scene-wide numbering is GM/assistant-caller-only because a player could infer the occupancy of hidden tags from skipped numbers. A separate pinned `summons` grant exposes `api.summons.place(presetId, x, y, summonerTokenId)` and `api.summons.dismiss(tokenId)`; player-callable GM-elevated code requires an exact approved preset allowlist, while all callers still pass live caster/scene/placement checks. These script actions commit separately and are **not** a transaction across the whole script. A world ZIP copy **or restore** invalidates imported script approval until the receiving GM re-reviews and republishes it. Workers are **not** hostile-code security sandboxes.
- **Summon lifecycle (partial SU-01–SU-08):** GM-indexed world actors and installed actor packs can be searched, toggled, filtered by source pack/PF1e CR and size, sorted, selected as a stable ref without placement, and saved as scene-bound private or player-published summon presets; a cancellable crosshair previews footprint, grid, range and sight through the shared SQ-10 module (shapes, its own fault list, named reuse) and refuses exactly what the host refuses, while the host still repeats authorization and placement checks. No source actor is permanently imported for a compendium placement. Each success atomically creates a **new linked actor+token**, owned by the actual caller rather than the elevated script, with its own bounded lifetime/instance marker; source media stays GM-only unless the owned hash is player-shareable. Dismissal, expiry, deleting either counterpart/scene, undo and reconnect preserve/clean exactly the intended instance. A published tile graph can invoke a private GM-authored preset on a player's authorized click/movement; source resolution after the graph commit is bounded and revision/caster rechecked, with failure disclosed only to the GM. The script worker can await a typed token result and dismiss only its caller's summons. **Not yet PF1e casting/resource/initiative rules, linked entrance/exit FX or an extensible per-system picker.**
- **Secrecy and media rights:** projected snapshots and updates retract/re-materialize hidden tokens, tiles and map pins; referenced media manifests and **each transferred chunk** follow current visibility and sharing consent. Private FX instances and GM-audience sequence macros never enter player snapshots or catch-up ops, and a revoked viewer receives only an opaque `fx.end`. Prefab instance, parent and source-scene flags stay host-only across creates, updates, scene-embedded-array updates, visibility grants and reconnect snapshots. GM-only graphs/code are absent from player replicas. Multiple writes to one object within a graph envelope now compute visibility crossings against the full pre-envelope state and deliver **one final create/delete**, so nested tag edits plus a hide/reveal cannot leave a stale token/tile on a player's replica. A deletion's pre-image is now used to project undo: a GM-only chat message ID is not sent to spectators, and mixed public/private undo envelopes no longer fail atomically on their replicas. The live Chat panel also refreshes on message **deletes**, not just creates/updates. World exports/imports preserve authored documents while imported JS loses authorization. FX uploads default to **GM-only playback and blocked world export**; the GM must separately attest player-serving and archive redistribution permission. Restricted FX blobs cancel ZIP/folder export rather than entering a half-valid archive. World export now also scans saved FX sequence/preset image and sound references: a referenced legacy asset without explicit export rights blocks, while unrelated legacy assets retain prior behavior. An imported world resets **both** FX rights declarations pending re-review. Legacy pre-wizard assets still need a broader rights migration/audit. Premium asset *platform integration* is not redistribution permission; no paid art is added to this repository.

## Try the integrated path

GM toolbar **Macros** → **Active zones**: expand **Create a rotated tile / zone in this scene**, enter its position/size and create it; choose the tile, enable **click** and optionally **Player click (published)**. Set **Trigger sort** (higher first on a tied movement crossing), change the initial selector to **Tokens in tile**, click **Add: forEach**, then use **Add inside loop** for a chat/tag/FX action (chat supports `{{index}}` and `{{currentId}}`). After the closing marker, add **filter → Tile trigger count** with optional maximum, **routeMethod** to a named **landing**, then save and optionally dry-run. For a relay, save a second **manual** graph on another tile, then add **collection → replace** (e.g. `This tile`) and **triggerTile** targeting that tile to the first graph; both graphs' world writes/history commit as a single undoable plan. Use **Add: Run All Batch Actions** after queued tag/visibility/door edits to execute that batch in order before subsequent steps; later changes to the same document form another batch, while the entire graph still commits or fails as one envelope. A child graph can start at a named landing. For an initially paused child, add **Set tile graph activity → Activate** for its tile immediately before **Trigger Tile**; the child sees the staged gate and the entire change undoes together. Tile visibility does not change, and a graph that deactivates itself completes its current fire. `{{originMethod}}` and `{{originTile}}` report the source event/tile in a child (while `{{method}}` is `manual`). Set the GM canvas layer to **Map** or **GM** to click it; a player clicks it directly in their canvas. Expand a saved zone's **Recent fires** for the last 100 invocations, or **Reset gates/history** to re-arm once/cooldown/max-run rules. **Add: set variable → Tile (persistent)** stores a bounded number/string/boolean value on the private graph (choose Assign or numeric Add; use the separate GM **Clear tile variables** button to erase the map). **Filter → Variable** reads staged changes in the same fire or the value carried over from the previous fire; graph actions and manual GM variable-clear share undo/history. Resetting gates does not erase these tile variables. Hidden tiles may respond to committed movement but are not clickable by players. Graph source, action list and trace never travel with the public tile-click request.

**Scene load path:** In GM **Macros → Active zones**, check **scene load** on a tile or region in the scene and tick **Player canvas triggers (published)** if players should fire it, then add a chat, tag or FX action. Each viewer that loads that scene — a player connecting, or a player returning after the table moved to a different scene while they were away — fires it once under their own identity (`{{user}}` names them, so FX can be aimed per viewer); reloading the same scene does not fire again, and a viewer who was already connected when the scene became active is covered by **scene change** instead.

**Environment trigger path:** In GM **Macros → Active zones**, check **lighting change** and/or **time change** on any tile or region, then add a chat or tag action. Moving **Settings → Ambient darkness** fires the lighting graph in that scene, and the **+1 hour**/clock buttons (or any graph's Game Time action, or a PF1e round wrap) fire the time graph in the active scene — one row per real change, silence for a same-value write, and no Simulate control because the events come from the world. `lighting change` reports the scene it belongs to; neither event carries a triggering token.

**Combat trigger path:** In GM **Macros → Active zones**, create or select any tile or region in the encounter's scene (combat events are scene-wide, so the anchor's position does not matter) and check **combat start**, **combat round**, **combat turn start**, **combat turn end** and/or **combat end**, then add a chat, tag or FX action. Start or advance the encounter in the **Combat** tab — each committed round/turn change fires every matching graph once, in Sort order, and **Recent fires** records entries like `combatStart · <user> · <token>`; `combat turn end` reports the combatant whose turn just ended while the other kinds report the current combatant. A combat-only graph offers no Simulate control (the events come from the world), and Undo of the encounter change never replays them.

**Door trigger path:** In GM **Macros → Active zones**, create or select a tile that covers a door and check **door open**/**door close** (add **door lock**/**door unlock** if the graph reacts to those changes too), then add a chat or tag action. Save and click the door with the wall tool on the GM layer — every committed change fires each matching graph once, in Sort order, and **Recent fires** records a `doorOpen`/`doorClose`/`doorLock`/`doorUnlock` entry. A door-only graph offers no Simulate control, because the event comes from the world; a published player plate that operates a tagged door can fire these rules too, while the player receives neither the graph nor the GM-only trace.

**World-clock branch:** In GM **Macros → Active zones**, add **Check Value → World-clock time of day**, choose `HH:MM` and a comparison/optional failure landing, then append a chat/action after each branch. The host reads the world's replicated settings, interprets 00:00–23:59 as minutes after midnight and wraps at each day boundary; it does not use the browser computer clock. GM **Settings → Advance clock** changes the committed time for the next fire. If the world clock has never been set, it is midnight; malformed stored clocks reject the whole plan. A connected player cannot directly write the clock or supply an event time; a GM-published tile can deliberately let them trigger a pre-authored Game Time change.

**Mechanical trap and script Revert path:** In GM **Macros → Active zones**, select a linked-token actor with PF1e HP, add **Hurt / Heal**, set a negative fixed integer, save a tile graph and fire it manually or publish a tile click to a connected player. The host spends temporary HP before HP; open **Chat → World actions** and press **Revert** on that specific trap to restore HP, temp HP, history and its message. Add a reviewed script step or run a saved reviewed script with world-writing Tagger/chat RPCs: the receipt groups committed writes (a failed later RPC leaves a marked partial action), and one Revert restores them without clearing the at-most-once script execution marker. No Revert during an active worker, and a subsequent actor/tag edit makes the affected action stale rather than silently erasing it.

**Game Time path:** In **Active zones**, place **Game Time → World clock change (minutes)** before **Check Value → World-clock time of day**. A value such as `90` advances the clock from 00:00 to 01:30 in the same graph; a later `-30` rewinds it to 01:00. Save and run or dry-run; Check Value, including in a manually triggered child tile, sees the staged time. Open GM **Settings** to see the replicated clock, and use **Undo** to restore the previous time together with the graph's message/history. Fixed minutes or safe dice/math formulas resolving to whole minutes up to ±one year are supported; a negative clock, clock beyond 100 years or shadowing legacy settings document rejects the entire run, not just the clock step.

**Move placeables path:** In **Active zones**, select pinned or tagged drawings/lights/sounds/templates, then add **Move**. Set coordinates mean the drawing bounding center or the emitter/template anchor; Add translates their existing position. Negative/dice offsets, snap and wall policies apply. These four types cut immediately, even with a duration/speed configured. GM and player replicas render moved drawings/templates/lights below fog; ambient sound playback itself remains unavailable. Undo or a named Revert restores the original geometry.

**Live Move destination path:** In **Active zones → Move → Destination source**, select **Live Tagger destination**. Choose tags, match/pattern, token/tile types and optional ref filters. X/Y are offsets from the staged destination point. Default choice requires a unique match; **Host chooses one at random** opts into 1–1024 matches. **Random within tile** samples its rotated rectangle per mover (token anchors still use their center). Earlier Tags/Move steps are visible; zero matches always reject, and ambiguity rejects unless random choice is enabled. Placement/offsets/snap can extend a mover beyond the destination tile; normal bounds/collision still apply without retries. Use **Include Move destination refs** to disambiguate, or author a unique tag. Saved queries reload; prefab templates such as `follow-{id}` bind to their own captured objects.

**Pinned target path:** GM **Macros → Active zones → Current collection → Pinned entities** lists untagged scene placeables too. Choose exact targets; selected references retain saved order. The Collection action also offers **Entities → Pinned entities** for Add/Remove/Replace. Unavailable saved choices stay visible; remove or replace them before saving. A disappearing target rejects the whole run rather than silently selecting something else. Prefab clones bind both pickers to their own captured objects.

**Condition/inventory path:** GM **Macros → Active zones**: select **Tokens in tile** or a Tagger token collection, add **condition** (`Prone`, Has or Lacks) and/or **inventory** (`Potion*`, a numeric comparison and matching *item-record* count), then add **filter → Entity count** before a chat/tag/FX action. Names are trimmed and case-insensitive; `*` is allowed only at the start/end of inventory names. The host reads linked actors live even when the actor is GM-only; an unlinked token cannot pass Lacks or zero items. Filtering itself exposes no actor data to players, but the GM's downstream public actions can intentionally disclose the branch result. Other game systems' status registries, stack quantities, expression-based conditions and trigger sources remain open.

**Tile data and per-token history:** In **Active zones**, add **Check Data** to compare a safe path such as `width` on the *triggering tile* even if the current collection is empty; set a failure landing for an alternate branch. Add **Filter by Token Trigger Count** after selecting tokens, set comparison `= 1`, then add **filter → Current collection count** to branch on tokens on their first fire. Each token keeps a separate private history; Reset Tile Trigger History re-arms them and undo restores the previous counts.

**Summoning path:** GM **Macros → Summons** filters indexed world actors or installed packs by name/keyword, pack, size and available CR; **Select reference only** shows its JSON ref without a world import. Choose one, set scene/range/size/duration/LOS, and publish a safe preset (or keeps it GM-only). Use **Pick on map…** to preview/cancel/place. In **Active zones**, add a `summon` step, choose that saved preset and a tile/trigger/current anchor; enable player click if appropriate. The graph history commits once, and the real linked actor/token is independently created after the graph transaction by the host. In **Script macros**, enable the `summons` grant, check the exact preset allowlist for player-callable GM code, review the source+policy, and call `await api.summons.place(presetId, x, y, casterId)`; a second script call can `await api.summons.dismiss(tokenId)`. Typed token inputs are selected from visible scene tokens. The GM retains private source/control and receives post-commit traces; the player receives only a safe callable catalog and their own independent actor/instance. A script's multiple world actions are not atomic; a zone summon cannot roll back graph history if compendium resolution later fails.
**Movement actions path:** In GM **Macros → Active zones**, create a tile under the mover, set the selector to **Tokens in tile**, then add **Move** with a point inside the scene — the host repositions every selected token with one update op per token (a token already at the point commits nothing) and the committed move goes through the same movement-trigger dispatch as a player drag, so a landing that crosses another tile can fire that tile’s enter/stop graph; add **Stop Additional Tiles Triggering** to suppress the sibling for the move that fired the graph. Two tiles that each move the token into the other are bounded by the host’s movement-chain depth cap (depth 8) — both graphs fire a deterministic, bounded number of times and a later manual fire still commits. **Rotation** sets an absolute 0–360° rotation on the current or triggering token (a no-change rotation commits nothing; rotating a token inside a tile can fire that tile’s rotate method). **Delete Entities** removes the current collection’s tokens/tiles/walls/drawings/map pins — one delete op each, other document kinds refused, a deleted token’s linked actor untouched, and the graph’s Undo restores the deletions. **Roll Table** rolls a GM-published scene table with the host’s own RNG and posts the result as a roll message to the **scene** or a **GM only** audience (the GM-only message never reaches a connected player’s store); the optional result variable stores the text (≤256 characters, a miss stores the empty string) for later filters and `{{variable}}` chat interpolation. Unit and host fixtures cover the whole contract; the Move authoring flow is additionally proven end to end in [`e2e/movement_actions.spec.ts`](e2e/movement_actions.spec.ts): run against the rebuilt production file through the documented D-222 workaround (npm-provisioned `@sparticuz/chromium` 153 with the package’s al2023 libraries on `LD_LIBRARY_PATH`, no security-bypass flags) it is 1/1, and the surrounding `active_zones` (16/16) and `action_revert` (3/3) suites re-ran green on the same byte-identical build (3,892,769 B).

**FX path:** GM **Macros → Assets / preview** filters owned image/video/audio files by name, MIME and hash, previews up to six side by side (≤20 MiB per preview), then **Use in timeline** assigns one to a section without copying the media. **FX timelines** authors a multi-lane cue, optionally selects source/target and **Follow visible token anchors**, marks it persistent, and runs it. A point anchor can be placed by clicking the map — **Pick on map…** next to X/Y (and To X/To Y) opens a cancellable crosshair with a cell/hex-centre snap and a live coordinate readout; cancelling, or closing the wizard with this draft, leaves the saved timeline untouched. **Preview on canvas** renders the unsaved draft on the GM's own canvas before anything is saved: it validates exactly like a save and never commits, so no player sees it, no `fxInstance` appears and Undo has nothing to do; **Stop preview** ends the local cue. **Live FX** lists host-owned instances and stops them without touching mechanics; authorized viewers regain an eligible aura after reconnect/reload. For uploaded media, the two separate sharing/export checkboxes default off; **Review existing media permissions** allows GM reapproval after a world import. ZIP/folder export refuses FX bytes lacking explicit redistribution rights. In **Script macros**, a reviewed `fx`-granted script can query `api.fx.list({ name: "ward*" })` and call `api.fx.stopMatching({ name: "Ward Loop" })`; all matching authorized persistent instances stop in one undoable envelope and reappear after undo. Alternatively, **Live FX → Stop matching live FX** accepts a scene, case-insensitive `*`/`?` name and/or exact saved sequence/source/target token IDs; an authorized GM/assistant stops up to 16 matching live instances atomically. The separate list search is only a preview, and a match over 16 is rejected without changes. For an executable chain, save short, nonpersistent timelines and use their saved IDs in a reviewed `fx`-granted script, e.g. `await api.fx.sequence().play("intro").parallel(api => api.fx.play("left"), api => api.fx.play("right")).playAndWait("outro").thenDo(api => api.chat.say("Done", "gm")).run()`. A cue must be scheduled to finish in ≤7 seconds (including host lead time) to be awaited; the Worker has a 10-second deadline. Earlier cues are **not** rolled back if a later section fails.

**Tagger rule path:** GM **Macros → Tags**: select up to 32 scene-qualified results with `{#}`/`{id}` templates already stored (use **Replace** to author them first), then click **Apply Tag Rules**. The host re-reads live hidden tags and allocates per-scene unique values in one undoable commit. The editing text field is not sent as a rule request. Players cannot invoke this GM-only allocation.

**Sequencer replay path:** GM **Macros → FX timelines**: add a text/image/sound one-shot, set **Section play count** to 3 and **Pause between plays ms** to 350, then save and run. This makes three separate clock-aligned plays of the same section; **Motion cycles** instead animates *within* one play. Persistent FX loops cannot also use section replays. A reviewed script may await the final play with `api.fx.sequence().playAndWait(id)`.

**Prefab path:** GM **Macros → Prefabs** captures scene objects and their linked tile graphs, chooses a root and a nested parent/lock for each child, previews bounds/media/reference failures, stamps two or more instances with fresh IDs and scene-unique `{#}`/`{id}` bindings, and lists/despawns entire instances. Token/tile root translation/uniform resize/rotation and root deletion atomically carry/cascade nested children and anchored graphs; undo restores all of them together. Hidden descendants and their media remain absent from player snapshots, reconnects and asset manifests. A GM-reviewed programmable macro may place an allowlisted template using `api.prefabs.place`, including a narrowly published player invocation. The prefab path still lacks **summons as prefab children, a full Sequencer programmable chain and sound/effect filters, non-token/tile root transforms, in-place attach/detach, and the complete MATT action registry**; this path does not satisfy full parity.
