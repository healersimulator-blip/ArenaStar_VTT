# PR #58 review — 2026-11-21

## Scope and verdict

Reviewed the merged [PR #58](https://github.com/healersimulator-blip/ArenaStar_VTT/pull/58)
("feat(strategic): Full VTT at Formation Scale (Phases A–E), 5,000×5,000 stitched maps & formation doctrine"),
one commit `91d72cd`, cumulative diff against `9df4f3d` (merged PR #57): **60 files, +15,106 / −1,360**
per GitHub. The checkout is at the merge commit, branch `arena/d08bdabb-arenastar-vtt`, clean tracked
following this review. No application fixes or GitHub comments were made as part of this review.

**Verdict: changes required in a follow-up.** The PR is a substantial, well-tested increment. It does the
right structural work — signed dependency manifests, a per-document conflict picture, atomic reconciliation
with single-step undo, general spell projection, and a wide range of Phase D live commands. But the Phase E
"conflict-aware reconciliation" is materially wrong in three places, concentrated in the flagship
token-deployment path this PR adds:

1. **Token deployment anchors are computed against two different conventions, inconsistent across the
   campaign builder, the launch projection, and the reconciliation write-back.** The campaign builder places
   tokens one half-token off the intended anchor, the hosted room spawns units at the anchor (not the
   rendered token), and the reconciliation write-back moves the token to a spot one half-token off the
   surviving models. The reconciliation preview and rollback paths never assert the write-back position.
2. **`skipConflicted` does not actually skip the actor write-back when the underlying army is conflicted —
   and says nothing when the army or unit simply no longer exists.** Actor spell/item/condition resources
   are still written back, so the "this document was edited since launch and is skipped" promise is only
   honoured for the unit/token branch (and then only for specific missing pieces).
3. **The GM-facing reconciliation preview overstates what will change** (every living unit counts as a
   "change"), and the conflict analysis silently ignores content documents (journals / roll tables /
   playlists / macros) even though the launch projection signs them as dependencies.

These are functional authority-adjacent defects in the PR's headline Phase E / token-deployment features.
They are not missing scope or design opinions; they are concrete, provable wrong-position and wrong-skip
behaviours in the shipped path. The main gate before describing Phase E as "conflict-aware" is fixing
findings 1–2.

## Findings

### 1. [P1] Token deployment anchors are computed against two different conventions, inconsistent across the campaign builder, launch projection, and the reconciliation write-back

**Locations:** `src/core/strategicRoom/campaignScene.ts:968` (token-path launch anchor),
`src/core/strategicRoom/reconcile.ts:171–174` (token write-back),
`src/ui/strategicRoom/CampaignBattle.svelte:303–304` (force-builder placement),
`src/canvas/tokens.ts:15–19` (`tokenRect`; token `x`/`y` is the CENTER).

`tokenRect(token)` returns `x = token.x - token.width/2`: a TokenDocument stores its CENTER. This is the
convention downstream code must respect. Three places in this PR get the math wrong or inconsistent:

- **Force builder (`CampaignBattle.svelte:303–304`)** places the token at
  `pxX = Math.round((anchorXFt / 5) * gridSize - gridSize)`. With `width = gridSize * 2`, the half-token
  is `gridSize` — so the token ends up one half-token west/north of the intended anchor
  (`anchorXFt = centerXFt - gapFt/2 ...`). The hosted scene is thus displayed with every unit one grid
  square off its intended deployment position.
- **Launch projection (`campaignScene.ts:968–971`)** computes the scenario anchor as
  `x: ((token.x + token.width / 2) / scene.grid.size) * 5`, i.e. it treats `token.x` as a TOP-LEFT
  coordinate and adds the half-width to recover its center. In combination with the force-builder's
  half-token offset, the launch anchor comes out near-correct (≈ `anchorXFt`) — a paper-cancelled pair
  of bugs. If either side changes, the room launches at the wrong anchor.
- **Reconciliation write-back (`reconcile.ts:171–178`)** writes
  `tokDiff.x = Math.round((u.at.x / 5) * gridSize - token.width / 2)` — again the top-left convention.
  The token's CENTER is then placed `gridSize` (one half-token, 5 ft) west/north of the surviving models.
  Note the full Phase E reconciliation test (`tests/strategicRoom/fullVttScale.test.ts:676–795`) never
  asserts the written token position or rotation; it asserts only the army stats, door, darkness, campaign
  binding and undoes/redoes the atomic envelope. So this mismatch ships undetected.

**Impact.** In the hosted room, the unit roster renders at the scenario anchor (hosted deploy ≠ scene
token). In the campaign scene after a battle, the reconciled token lands one half-token off the surviving
model position.

**Fix.** Pick one convention (center, matching `tokenRect`) and apply it consistently:
scene tokens at `px = round(anchor_ft / 5 * gridSize)`, launch anchor `anchor_ft = token.x / gridSize * 5`,
reconciliation write-back `tokDiff.x = round(at.x / 5 * gridSize)`. Assert the write-back token position in
Phase E tests.

### 2. [P1] Reconciliation's `skipConflicted` does not skip the actor write-back when the underlying army is conflicted, and silently omits conflict records for missing/unknown units

**Location:** `src/core/strategicRoom/reconcile.ts:131–208` (unit loop), `src/core/strategicRoom/reconcile.ts:117` (`isBlocked`).

The army-unit branch gates the unit write on `isBlocked("armies", src.armyId)` and bumps `skippedConflicts`.
But the **actor write-back** that follows — `system.pf1e.spells.slotsUsed` / `prepared` / item charges /
conditions, lines 188–282 — is unconditional with respect to the unit's army conflict. If the GM checks
"skip conflicted documents when applying" (the default), an army that was edited after launch gets no
unit write-back, but its actor still has its spell slots decremented, items charge-cloned down, and
conditions merged in. The GM's own flagship promise ("any document edited independently since launch is
skipped rather than overwritten") is not honoured for the actor branch, which still writes — and is
observable in the atomic envelope.

A second, related gap: if the army document or the specific unit is deleted after launch
(`army?.units.find(...)` returns `undefined`, line 138), the unit is **silently** skipped — no conflict
record, no `skippedConflicts` bump, no entry in the preview's `reconciledUnits`. The reconciliation audit
(`lastHostedBattle.reconciledUnits`) and the preview's "Units: N" count both undercount without any
signal to the GM.

**Impact.** `skipConflicted: true` does not mean "nothing from the conflicted army is written"; it means
"the army's unit is not written". Item/spell/condition drift from a concurrent edit lands.

**Fix.** Either skip actor-resource write-backs for any unit whose army/token was skipped, or emit a
conflict record for missing army/unit/token documents. An actor that is a real (non-conflicted) document
can remain writable, but its "which unit was at fault" provenance is lost.

### 3. [P2] Reconciliation preview and conflict analysis overstate changes

**Locations:** `src/core/strategicRoom/reconcile.ts:86–88`, `:44–45`, `campaign.ts:69–75`, `reconcile.ts:96–98`.

- `unitChanges` counts every unit with **any** living model as a change (`u.at !== null`), and `at` is
  non-null whenever `alive > 0` (`campaign.ts:69–75`). So the GM's preview shows the whole surviving side
  as "changed", even for the turns where nothing changed (initial strength == alive == the same anchor
  position). The toggle for whether a unit *changed* is lost.
- `analyzeBattleReconciliation` ignores dependencies whose `coll` is not `scenes`/`armies`/`factions`/`actors`
  (`:45`), even though the launch projection explicitly signs and stores `journals`, `rollTables`,
  `playlists` and `macros` dependencies (`campaignScene.ts:projectCampaignContent:513+`). The GM sees no
  conflict signal for content that was edited post-launch. This is informational rather than data-loss-y
  (the reconciliation never writes content docs), but the per-document conflict picture the PR advertises
  as "conflict-aware" is incomplete.
- A related subtlety: `unitChanges`/`actorResourceChanges` counts a unit as an "actor resource change" if
  `conditions?.length > 0` — which is true for every unit with a launch-time condition (e.g., `"Entangled"`
  from a pre-battle state), regardless of whether the condition was added during the battle. This
  mis-states the preview.

**Impact.** Preview numbers do not faithfully represent what will be written; a GM scanning the preview
cannot tell a one-killed-unit battle from a full-side wipe.

**Fix.** If your scope is "the battle produced observable changes", seed the count from actual deltas
(`initialStrength !== alive`, spell/item spent counts, conditions added since launch). Either include content
dependencies in the conflict list or make it explicit in the PR/UI that only scene/army/faction/actor edits
are surfaced.

### 4. [P2] Force-builder overwrites all scene tokens, resizes the scene, without confirmation or undo prompt

**Location:** `src/ui/strategicRoom/CampaignBattle.svelte:241–394` (`deployForcesToScene`), specifically `:361–381`.

The button reads "Deploy N units to scene", but the action is destructive:

- `tokens` is replaced with only the newly-deployed batch — **any hand-authored or unrelated scene tokens
  are silently destroyed** (`diff: { tokens, ... }` at `:371`). No `confirm()`, no draft, no preview of the
  result.
- `width`, `height`, `grid.size`, and `tiles` are all rewritten — the scene is resized and re-gridded to
  fit the force, silently. Stitched floor tiles are preserved but rescaled (`scaleTileX/Y`).

The token-anchor math bug identified in finding 1 compounds the damage. A repeat-launch still overwrites
the entire scene's default grid every time the button is pressed.

**Fix.** (At minimum) `confirm()` before destructive overwrite, or add a `replaceTokens: true` safety flag;
and if the intent is force deployment onto a new canvas, use `width/height` only when the user accepts it.

### 5. [P2] `projectSpellHazardAction` hardcodes `5 ft × 5 ft` grid/distance

**Locations:** `services/strategic-room/src/resolve.ts:344–349`, `src/core/strategicRoom/pf1eActionProjection.ts:121–127`.

Both `projectFrozenEntangleCast` and the frozen-hazard branch of `resolve.ts` hardcode
`grid: { size: 5, distance: 5, units: "ft" }`, and the validator in `pf1eActionProjection.ts:153` rejects
anything with `grid.distance !== 5`. Today the strategic grid is always 5 ft (`CELL_FEET = 5`), so the
constant is correct in practice. But this is a copy-paste indirection: a future re-scaled room (e.g., a
10-ft or 25-ft grid) would fail with an obscure "only a resolved, host-verified ... area can be projected"
error instead of a clear "unsupported grid".

**Fix.** Deriving the grid from the frozen scenario's `bounds`/`scene.grid.size` (or from an explicit
`grid` parameter on the projection call) would remove the brittleness.

### 6. [P3] Documentation vs code: zoom-limit mismatch in PR text

**Location:** PR #58 body ("Supports … `MIN_ZOOM = 0.01`"), `src/canvas/camera.ts:25`, `src/ui/strategicRoom/HostedMap.svelte:255`+.

PR #58 body and the `docs/STRATEGIC_FULL_VTT_DESIGN.md` header describe `MIN_ZOOM = 0.01`; the code defines
`LARGE_SCENE_ZOOM_LIMITS = { min: 0.002, max: 10 }` and `HostedMap` clamps zoom to `{min: 0.002, max: 12}`.
`MIN_ZOOM` does not exist anywhere. Either update the docs or the constant.

### 7. [P3] Force-builder stitched panel deploys are silently dropped when oversized

**Location:** `src/ui/strategicRoom/CampaignBattle.svelte:442–535` (`withBackgroundTiles`).

For oversized panels (> `MAX_SCENARIO_BACKGROUND_BYTES`), the path compresses the image (`img → canvas →
web-webp`). If compression returns null (e.g., `document` is undefined in a non-browser context, or
`ctx`/`cv.toBlob` fails), the panel is silently dropped from the scenario — the notice doesn't say which
panels were dropped. The user sees only "Battle ready". Similarly, `withBackground` has explicit warnings
for the background art case, but the tile path does not.

**Fix.** Surface dropped-panel warnings through `notice`, consistent with `withBackground`.

## What is already good

- **Signed dependency manifest** (`scenarioProjectionDigest` + `dependencies` + `sourceSeq` +
  `scenarioProjectionDigest` re-validated by `parseScenario` at launch, and again in `frozen()` after
  scenario mutation) is a clean integrity design. `<secret>` blocks are stripped on public journals and
  GM-only content is forced server-side (`op === "gm" && member.role !== "GM"` returns
  `forbidden`).
- **One-time invites, sealed at rest** (`invite.ts`, `postgres.ts:342–345`): `sealInvite` with per-room
  AAD, 30-minute expiry, one-time claim, GM-recoverable copy via `invite_cipher`. `member.invite` rejects
  claimed seats. The full GM role-gate (`if (member.role !== "GM") return deny(...)`) covers
  `unit.faction`, `roster.assign`, `member.*`.
- **`member.kick` vs `member.revoke`** are properly separated; kick leaves the seat intact, revoke
  bans and deletes control + current orders.
- **Atomic reconciliation write-back with single-step undo/redo** — `commitBattleReconciliation` marks
  ops in `battleWrites`, sets `reconcilingBattle = true` around `commitOps`, and `audit` includes the
  single receipt; `undo()`/`redo()` round-trips the whole envelope. This is the right shape for the
  "finish battle" UX.
- **Authority decisions are server-side, not client-side**: `BattleView.validate` checks unit ownership +
  `control`, `canToggleDoor` checks 25-ft proximity (with GM bypass), `member.update` re-derives both
  factions, `roster.assign` clears orders and requires both factions to retain a unit, and the view is
  built from HMAC-projected cohorts, not client-computed.
- **`orders.submit` idempotency + replay protection** — requestId digest + the strict
  `DELETE + INSERT` order replacement, with bounded concurrent edits (`MAX_EDITS = 25`).
- **Phase D live commands are gated by role**: `scene.light`/`scene.template`/`scene.playlist` GM-only;
  `scene.door` checked via `canToggleDoor`; `chat.send` faction/public/GM scope enforced (gm scope requires
  GM role); hidden lights never leak to non-GM clients; GM-only roll tables bounce player attempts.
- **The `before`/`after` scene variants for conflict detection** correctly strip launch-binding state
  (`normalizedSceneForLaunchCheck` removes `campaignBattle`/`strategicActionCards`/`lastHostedBattle`),
  so the conflict comparison is fair across a launch→finish cycle.
- **`commands` in `postgres.ts` are Idempotent + in transaction `FOR UPDATE`** (`SELECT … FOR UPDATE` on
  the room) — distributed admission is safe; `admit()` uses compare-and-set on the invite row.
- **`orders` are frozen at freeze time** (`beginFreeze` → `strategic_frozen` with scenario + control snapshot),
  so post-freeze `unit.faction`/`roster.assign`/`member.update`/`roster.assign` can no longer rewrite
  past turns.
