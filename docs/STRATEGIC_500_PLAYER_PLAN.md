# Scaling Arena Star to 500 strategic players

**Research and recommendation · 18 November 2026 · Baseline: `15aec7a`**

## Recommendation

**Strategic mode should be the full VTT operating at formation scale, not a reduced battle
service.** Hosting changes authority, persistence, projection and dense simulation—not campaign or
PF1e meaning. The `ModelPool` is a high-density projection of authoritative campaign documents, not
an alternative schematic world. See
[the canonical full-VTT strategic design](STRATEGIC_FULL_VTT_DESIGN.md).

Build an **optional hosted strategic room**, with one authoritative room process per battle, binary WebSockets, and the existing TypeScript simulation running off the connection thread. Keep the browser-hosted WebRTC mode for small tables. **Do not move the current broadcast path to a server unchanged.** The changes that make this viable are private, batched orders; deterministic spatial queries in the resolver; and compact, permission-filtered views instead of pushing full reports to everyone.

The target is **500 connected commanders × ~100 models each = 50,000 models**, organized into **2,500–5,000 units**. Arena Star already has the right performance model: units are documents, while dense model state lives in a columnar `ModelPool`, not in 50,000 token documents. This optimization does not remove the battle's links to scenes, actors, tokens, items, spells, effects, walls, doors, terrain, floors, lighting/vision, templates, reactions, FX or campaign content; those remain authoritative inputs through a validated projection and scale-specific adapters. The research assumes one shared battle, simultaneous **turn-based** orders, two factions in the probes and a small number of shared visibility groups in the first release. A game in which all 500 players have separate fog of war, continuous realtime PF1e, or everyone must stream all 50,000 models at all times is a different performance target. None of those assumptions changes the requirement to keep all 50,000 models in the authoritative simulation.

**Status at this baseline:** A 50,000-model battle fits the deployment count and some turns resolve in seconds in isolation. The existing end-to-end path is not ready for 500 players. No 500-player room has been qualified over a network. See the [pilot implementation and newer diagnostics](STRATEGIC_500_IMPLEMENTATION_PLAN.md#5-pilot-verification) for follow-up.

## What we measured

These are diagnostic measurements on the same Linux sandbox (2 vCPU, Intel Xeon 2.60 GHz, ~3.85 GiB RAM, Node 22.22.3), not production benchmarks. The [reproducible probe](../performance/strategic/legacyProbe.ts) uses the actual PF1e rules, sim codec, and host paths. The prior [scale evaluation](SCALE_500_PLAYERS_EVALUATION.md) used different synthetic worlds; its timings are not directly comparable. The existing [10k golden gate](../tests/sim/strategicGoldenGate.test.ts) uses 20 units, so it does not exercise thousands of unit-level lookups or hundreds of armies.

### Simulation: 50,000 models, 500 armies, two factions

| First-turn workload | 2,500 units × 20 models | 5,000 units × 10 models |
|---|---:|---:|
| Idle, no orders or combat events | 0.99 s | 1.05 s |
| All units in paired melee engagements | 2.18 s | 3.59 s |
| Mixed: 20% melee, 10% ranged, 10% march, 60% hold | 12.18 s | 33.27 s |
| All units march 10 ft on open ground | Cut off at 35 s | Cut off at 35 s |
| Optional automatic doctrine, opposing formations already in reach | 12.07 s | 17.33 s |

Timings cover `SimRunnerCore.resolve`: rules, analytics, compaction, stats, hashing, and checkpoint/delta creation, but not worker transfer, storage, host publication, or display. Each table entry is one cold turn, not a percentile. The mixed runs recorded 23,196 and 23,378 attack attempts, and the melee runs over 72,000 each. The 5,000-unit mixed turn spent 32.03 s inside the rules hook, already above the current [30 s worker timeout](../src/workers/simWorkerClient.ts#L42). The all-march cuts include ~0.5 s of setup; neither reached the end of the rules hook. One CPU profile of the 2,500-unit mixed run attributed ~59% of sampled time to `marchOpportunities` and its callees, with ~14% marked as garbage collection separately. In contrast, per-army forecasts used 1.40 s of the 5,000-unit melee turn (~39% of total), so movement optimization alone won't cover every case.

**A map-size bug matters before any performance tuning.** The [codec](../src/sim/codec.ts#L65-L71) silently clamps positions to signed 16-bit values at 1/16 world-unit precision: roughly **−2,048 to +2,048 per axis**. An initial fixture exceeded this range and collapsed formations onto the boundary; those timings are discarded. The table uses a centered layout and checks decoded position bounds and one model per square. Production's [fallback deployment lanes](../src/sim/deploy.ts#L119-L145) extend by 250 world units per same-faction unit, so relying on them for a large battle can hit the same clamp. Reject unrepresentable deployment/movement in the short term; version the coordinates (e.g. signed 32-bit fixed point or sector-relative offsets) for the hosted mode and test round trips at extents. Make this a correctness gate, not a map-authoring workaround.

### Authority, replication and transport

| Probe | 2,500 units | 5,000 units |
|---|---:|---:|
| Last-minute order submissions, 500 connected sessions | 50 batches sampled: **11.75 s** | All 500 batches: **116.10 s** |
| Per-batch host processing, p50 / p95 (excludes time waiting behind other batches) | 223 / 290 ms | 225 / 274 ms |
| Melee turn, advance to report phase after framing all 500 copies | 10.30 s | 22.78 s |
| Of that, time after the sim core returned | 8.27 s | 19.52 s |
| Total application bytes framed to the 500 players, report + sim delta (decimal) | 627 MB + 16 MB | **1,701 MB + 104 MB** |
| 10 sequential reattaches, including requested sim snapshots | 4.32 s | 4.31 s |

- **Orders:** one legitimate private order batch per submitting player, up to 10 unit edits, sent back-to-back through actual `HostSync` validation and commit. In the full burst, the sink counted only ~0.64 MB of input and ~0.66 MB of outgoing Ops, all to the authors. Despite that, the manifest source was consulted **500,000 times** and not a single manifest update was sent. [The commit path](../src/host/sync.ts#L4449-L4510) currently projects asset entitlement twice per session; each call walks the projected world for players. Eliminate work on unrelated writes before worrying about faster sockets. [Ready state](../src/host/turnChannel.ts#L397-L405) also broadcasts a growing roster on each update; that path was not in the order burst.
- **Results:** only **74.7 KB** of compressed authoritative sim delta versus **3.47 MB** for the full GM report in the 5,000-unit melee turn. Players got projected results through the real [`TurnChannel`](../src/host/turnChannel.ts#L1081-L1163), but both factions saw much of this close-contact fixture; average player frames were ~209 KB for the delta and ~3.40 MB for the report. Projected deltas can be *larger* than the unprojected delta: the codec can replace a full-column encoding with runs of visible indices. Reporting and audience fan-out, not the raw `ModelPool` size, dominate this sample. Framing once per shared audience would reduce CPU, **not** the sum of bytes sent to 500 clients. Replace the default report push with a bounded summary. At the current 1.805 GB per turn, even a 10 s send window needs ~1.44 Gbit/s aggregate payload egress, before further compression, transport overhead or assets.
- **Rejoin:** reattaching 50 provisioned users for document snapshots alone took ~56 ms in the 5,000-unit burst. Adding the real sim snapshot request is far more expensive: the 10-user sample took ~4.3 s, emitting ~54 KB of sim data per player (5,000 units), plus their document snapshots. The non-GM [snapshot path](../src/host/turnChannel.ts#L1267-L1304) snapshots the pool, separately rebuilds visibility using another snapshot, and then encodes each player's view. Reuse safely scoped snapshots by version instead of doing this during a reconnect storm.
- **WebRTC headroom:** in Playwright's Chromium **153.0.8010.0**, one page retained 500 fresh `RTCPeerConnection` objects; the 501st constructor threw `Cannot create so many PeerConnections`. This is consistent with Chromium's source [3](https://chromium.googlesource.com/chromium/src/+/44dcbd18a9567c6536cdf3e4c0a612c0340fe6fa/third_party/blink/renderer/modules/peerconnection/rtc_peer_connection.cc). No offers, ICE, data channels or traffic were involved. It is not a universal browser limit or a throughput result. The current host opens one connection and four data channels per remote peer. Even if 500 fit on this build, there is no spare connection at that count for churn or extra peers.

The 500 sessions above were preauthenticated counting transports; the turn probe uses the inline sim runner and fake IndexedDB. No TLS, ICE/TURN, HTTP assets, congestion, client parsing, render time, actual durable commit or fresh-user admission was measured. There are no hero actors, spells, walls, multiple floors, chat bursts or media transfers in these fixtures. Paired combat verifies populated engagements, not a dense continuous front. Doctrine at range (which can synthesize marches), clustered long-reach units, rich spells and wall-heavy scenes still need explicit cases.

## Why this architecture

| Option | What it solves | Main trade-off |
|---|---|---|
| Optimize the existing GM-browser WebRTC star | Useful local improvements, keeps offline/self-hosted play and no new service | A tab still owns all RTC links, upload, authority and recovery. No headroom in the tested Chromium build. Not the 500-player production path. |
| Browser authority behind a WSS relay | Fewer direct RTC connections and less GM uplink if the relay can multicast authorized frames | The browser still owns validation, sim, visibility, and persistence. A blind relay cannot decide who is entitled to what; browser suspension/exit still stops the room. Useful bridge if server authority is prohibited, not the default 500-player design. |
| **Hosted authoritative strategic room** | Removes the GM tab as a single connection and durability bottleneck, supports bounded queues and reconnects, can scale different rooms independently | Requires operating or self-hosting a service, server trust and durable storage. Projection and rules still need optimization. **Recommended.** |
| Multiple writers or distributed simulation for the same battle | Potential last resort if one measured authority cannot meet the budget | Cross-front movement, shared visibility, initiative and seeded combat couple the state. Adds reconciliation and recovery risk before any evidence it is necessary. |

Use a small TypeScript/Node room service with a WSS adapter behind the existing [`Transport`](../src/core/net.ts) boundary and versioned strategic messages. A regular Node process with [`ws`](https://github.com/websockets/ws) is enough for the first load test; a framework is not necessary to prove the design. WebSockets carry binary frames, but `bufferedAmount` measures data queued, not delivered; use app-layer flow control ([WHATWG](https://websockets.spec.whatwg.org/#dom-websocket-bufferedamount)). Start without per-socket compression; measure compression once per reusable frame rather than assuming permessage-deflate is free [2](https://github.com/websockets/ws/blob/master/README.md). Consider WebTransport streams/datagrams only if measured ordered-stream contention justifies another transport [1](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API). Move voice/video, if added, outside the battle state channel.

### Hosted room: three different data paths

1. **Commands and durable state.** One logical writer per room, one authoritative order per unit/revision. GM and players are both clients; the server binds roles/command rights to admitted identities. Reuse `HostSync` authorization, seeded PF1e resolution, and the pure turn reducer; introduce a versioned `submitOrders` batch (`turnId`, expected revision, idempotency key, up to the caller's authorized units). Validate scope and rules, privately ACK the accepted revision after durable write, replace drafts instead of appending every drag, and coalesce readiness into a count or small scoped update. Close orders and freeze the winning revisions, checkpoint reference, rules/schema version and seed in one durable barrier. Decide late-order handling by server acceptance at the barrier, not client clocks. Block generic unit-order writes in this room, so neither UI nor agent scripts can bypass the barrier. Return explicit stale/locked responses. Use a transactional store (e.g. Postgres) for the accepted journal and result pointer. Store checkpoints and private raw reports as durable blobs, with checksummed references. Commit the result and any hero/world effects once before publishing. Recover a frozen turn with the same inputs after a crash; use a fenced writer generation when introducing failover so an old writer cannot publish a second result.
2. **Simulation and authorized views.** A dedicated CPU worker owns the typed arrays and returns a versioned result. Reuse `SimRunnerCore`; replace browser Worker, IndexedDB and blob-loaded rules at the seams in [`SimBridge`](../src/host/simBridge.ts) and host boot. Node [worker threads](https://nodejs.org/docs/latest-v22.x/api/worker_threads.html) isolate CPU work from socket I/O and can transfer owned buffers, but aren't a security sandbox. Use vetted, pinned rules packages in v1; don't run arbitrary uploaded JS in the server process. Compute the visibility map and read-only view once per state/ACL/geometry version and identical audience. Compose shared unit summaries, faction/sector detail, private order/readiness/whisper feeds and a privileged GM view. Never use a faction key for data that is only available to specific owners. Build stable model-ID enter/update/leave messages for authorized nearby models; camera/zoom subscriptions narrow a view, never grant permission. Revoke old subscriptions on membership changes, reset the version, and rebuild from the current authorized baseline on a gap. Do not send indexed hidden slots, raw historical ops, or unredacted reports to players. Audit report text, nested analytics, counts and details too: the [current paged detail path](../src/host/turnChannel.ts#L1307-L1334) reads stored events and does not apply the broadcast report's projection. Both paths need the same explicit history/disclosure policy before exposing them through the room service.
3. **Presentation and delivery.** Push the result version, limited visible summaries and the state necessary for the player's view. Fetch authorized report pages/replays and media via HTTP; don't block the reliable command lane behind multi-megabyte frames. Use a shared asset cache/CDN for public files and entitlement-checked URLs for private files; a hash is not permission. Index asset references and invalidate entitlement only for changes affecting it (including hidden-reference changes and role/fog changes). Retain the current Pixi [particle/LOD path](../src/canvas/layers/ModelLayer/index.ts), but render units/armies at distance and only local authorized models at close zoom. Use dirty bounds and spatial viewport queries instead of rebuilding a 50k-model hash and walking candidate units on every camera change. Buffer and interpolate presentation on clients; clients do not resolve authoritative damage. Bound queue bytes, input sizes and in-flight snapshot work per connection and room. Coalesce replaceable presentation updates before enqueue; never drop a durable ACK or an incremental update without a resync barrier. Slow peers resync or disconnect instead of delaying the room. Cap or scope high-rate cursor/ping presence separately from authoritative state.

## Build order

1. **Make the workload safe to measure.** Turn the included probe into a repeated perf fixture with recorded hardware and versioned layouts; validate coordinate range and unit/model mapping. Add privacy and freeze tests before adding cached/deduplicated views. Repair the existing [M2 E2E](../e2e/m2.spec.ts) roster selector (the earlier smoke test stopped before deployment) and add the actual many-unit workload. The `DetectionGrid` [31-faction ceiling](../src/core/detection.ts#L142-L151) is a separate requirement if the campaign needs more than 31 actual factions, not a limit of 31 players. Consider sparse cells if large extents would make a dense grid expensive.
2. **Fix the resolver's cost per order.** Start with the measured movement path. Replace `units.find`/`.some`/`.indexOf` with order-preserving indexes for unit/army/squad/leader data. Replace per-march rebuilds of *all* opposing threat sets with a cell-to-reactor index or a conservative spatial query of the walked cells. Preserve pre-move simultaneous geometry, deterministic reactor/RNG order, living state and spent opportunity budgets as reactions resolve. For doctrine, calculate anchors once, find the exact nearest enemy anchor with stable ties, then test model pairs only for the chosen opponent; use the index for envelopment and local wall/spell queries as needed. Collect analytics once per turn and bucket by army rather than rebuilding the whole report per army. Then profile compaction, pool copies and serialization. Use the old/new canonical hashes, unit diffs, events and rule evidence as parity checks; compare dense and sparse fixtures. Don't switch to aggregate combat, rewrite in Rust/Wasm, or shard a battle to optimize an unmeasured bottleneck.
3. **Remove work proportional to `orders × viewers`.** Implement private batch/phase ACKs and eliminate the two whole-world asset projections for order-only changes. Index entitlements with revocation tests. Publish one pre-encoded frame per *identical* authorized audience and state version, and give sessions direct subscriptions rather than scanning the full session list for each user. Make result pushes bounded by design; detailed events stay available on demand. Test owner-only data, newly visible models, loss of detection, permission changes, reconnect/resume and the join storm before promoting these changes. This work benefits the small-room path where applicable.
4. **Wire up and qualify one hosted room.** Run the optimized authoritative path using real WSS, durable order/turn storage and the worker, first at 100, then 250, then 500 active clients. Keep one authority for the battle; distribute independent rooms first. Only add stateless fan-out gateways if socket/egress measurements require them. Only parallelize or partition the sim if the optimized worker still misses the rule budget and deterministic phase boundaries are understood.

## Proposed release gates (not achieved)

Publish a reference rig and workload before collecting qualification numbers. Start with a dedicated regional host (e.g. 8 vCPU, 16 GiB RAM, 1 Gbit/s NIC) and separate generators. Exercise both 50k shapes for at least 50 turns and repeat cold/warm. Use headless protocol clients on real TLS connections plus representative real browser clients (including the GM) for replica and rendering behavior. Sample reachable WAN paths and shape a baseline such as 80 ms RTT, 1% packet loss and 10 Mbit/s downstream; add throttled peers and 50 simultaneous reconnects during turn close. Run mixed combat including hero/spell/terrain and optional doctrine if advertised, all-move, an all-visible battle, and a dense front; also test 600 connections and a long soak for headroom. Instrument server queue delay, ACK round trip, freeze/resolve/commit/project/send latency, client-applied result time, event-loop lag, bytes by lane, held buffers, heap and client frame time separately.

| Gate | Initial budget to agree on and verify |
|---|---|
| Orders at the deadline | 500 unique batches arrive over 2 s. Client-to-durable-ACK ≤250 ms p95 / ≤1 s p99 on the baseline network. No acknowledged order is lost, reordered into the wrong turn, or applied twice. |
| Turn completion | In normal supported 50k workloads: close to durable publish ≤5 s p95 / ≤10 s p99; measure time to apply separately (target ≤2 s p95 after publish). No timeout in the declared supported stress matrix. The GM can see a resolving/paused state without blocking orders UI or network maintenance. |
| Delivery | Budget ≤128 KiB p95/player for the default turn push (summary plus subscribed state, not full optional reports). At 500 × 128 KiB that's 62.5 MiB per turn or ~262 Mbit/s over 2 s before overhead. Prove fairness and bounded steady-state memory with slow receivers, concurrent snapshots and media fetches. |
| Reconnect/recovery | 50 concurrent reconnects, active authorized view usable ≤5 s p95, without breaking healthy clients' ACK SLO. Kill the authority before/during/after resolve and publish: no lost durable ACKs, no duplicate effects and matching canonical results; test stale-writer fencing. |
| Browser and privacy | On a published reference laptop, aim for ≤33 ms p95 frame interval during play (roughly 30 FPS or better), including pan/zoom and applying results. Assert no hidden models, reports, assets, identifiers or private orders in other audiences' frames. Verify before and after reveal, revocation, reconnect and role changes. |

Continuous realtime is not covered by these gates. For perspective, even a 128 KiB per-player payload at 5 Hz would exceed 2.6 Gbit/s at 500 clients. PF1e's current [`tick` hook](../src/packages/massBattlePf1e.ts#L2016-L2023) is also not a realtime combat implementation. If realtime is required, define a tick budget, model-delta frequency, density and interest-size limits separately before committing to a transport or sim design.

## Reproduce the diagnostics

From the repo root after `corepack pnpm install --frozen-lockfile` (Node 22; no service is started):

```bash
corepack pnpm bench:strategic matrix 1
corepack pnpm bench:strategic turn 500 10 contact
corepack pnpm bench:strategic fanout 500 10 50
# Full synthetic browser-host command fan-out:
corepack pnpm bench:strategic fanout 500 10
```

`sim` checks decoded geometry and uses seed 4242. `turn` uses the channel's normal derived seed, a pre-deployed layout and 200 manifest entries, and exercises the actual sim report/delta fan-out and ten sequential sim reattaches; it does not exercise the full initial deploy-to-everyone snapshot broadcast. `fanout` pre-attaches 500 already provisioned players, submits one batch each (or the first N with the optional limit), then reattaches 50 for document-only snapshots. The counting transports discard frames after counting and implement no backpressure. The RTC constructor spot-check is reproducible via a Chromium Playwright page: keep each `new RTCPeerConnection({ iceServers: [] })` in an array until construction fails (or 550 constructions), record `browser.version()` and close each object; use the existing Playwright config for sandbox browser libraries. These diagnostics identify where to invest, not an acceptance run.
