# PR #54 review: bringing hosted battles into ArenaStar

Reviewed the [merged PR](https://github.com/healersimulator-blip/ArenaStar_VTT/pull/54) at `8865cb2` against first parent `15aec7a` (2026-11-19). **Target: the GM opens a strategic scene in an existing campaign and clicks Launch.** The same VTT scene becomes the live battlefield. The target audience is 500 commanders plus the GM. No second world, scenario export/import, operator CLI step per battle, or separate GM tab. The service is an execution backend for the scene, not another campaign.

## Findings to address

1. **Order submission can get stuck before sending.** In [`HostedRoomClient.submit` / `sendPending`](../src/client/hostedRoom.ts#L380), the client reserves `pending` before checking socket backpressure. Above `MAX_FRAME` it returns `false` without sending or publishing a retryable status. The [orders form](../src/ui/strategicRoom/HostedRoom.svelte#L134) ignores the result. If the connection stays open, draining the buffer does not retry; subsequent submits see `pending` and do nothing. Distinguish “never sent” from “sent, commit unknown”: release the reservation and show a retry notice in the former case, retain the original request ID in the latter. Test a temporarily full open socket, then drain and submit, asserting one send and one accepted revision.
2. **The world extractor accepts incompatible map units.** [`worldExtract.ts`](../services/strategic-room/src/worldExtract.ts#L41) requires square cells of distance `5`, but does not read `grid.units`. The [extraction fixture](../tests/strategicRoom/core.test.ts#L230) omits units altogether. I ran the built CLI on a two-army scene marked `units: "m", distance: 5`; it wrote a scenario successfully. Hosted coordinates and deployments are in feet. Require documented feet units before copying anchors; reject ambiguous or unsupported units rather than silently changing scale. Cover feet, metres and missing units, including a fixture from the real VTT export path.
3. **A shared offline bundle has no size headroom.** With frozen pnpm installs, the first-parent single HTML measured **6,821,964 bytes** and the merged HTML **6,834,717 bytes** (+12,753). Both fail the **6,291,456-byte** [`size` gate](../scripts/size.mjs). This is pre-existing, not evidence that the pilot UI was accidentally shipped in the VTT. Keep a separately built hosted entry while recovering the offline budget; measure the actual artifact, not just source imports.

It uses the browser identity helpers, but a hosted seat requires admission at the service origin. |
| Write and save | GM `HostSync`, world documents/OpLog, local persistence; `TurnChannel` and `SimBridge` own local battle progression. | [`StrategicAuthority`](../services/strategic-room/src/authority.ts) and PostgreSQL own commands, revisions, frozen input and publication. The client gets a membership-filtered baseline, region details and report pages, not world documents. Both shells already use turn-progress presentation. |

The tactical media cache in #54 improves the peer path. It isn't a reason to send world assets or persist private hosted views in a shared cache.

## Proposed in-scene launch

1. **Launch from the scene, not the start screen.** In [`App.svelte`](../src/app/App.svelte), branch on the active scene ID and `flags.core.scale`. For a strategic scene, offer a GM-only **Launch multiplayer battle** action. Show participating factions, commander assignments, and which scene features the pinned pilot rules can represent. Refuse incompatible geometry, units or mechanics before launch. Do not silently substitute a blank demo battlefield. For the first release, launch from setup, not halfway through a locally resolved turn.
2. **Provision from live campaign data.** Send only the selected deployment and assignment data to an authenticated service. Reuse the scenario validator, not world ZIP I/O. The pilot currently runs one configured room per service and provisions by CLI. Add a provisioner/room router or allocate an instance per battle behind the proxy. Authenticate the GM's provisioning entitlement independently of the local GM UI. Use an idempotent launch ID so retries after a lost response resume the same battle. Store a non-secret battle reference against this world and scene; keep invites, bearer tokens and signing keys out of the scene document and saves. A copied world must not inherit control of a live battle.
3. **Render inside the current VTT.** Keep the campaign shell and scene navigation mounted. Replace only the selected scene's board and turn controls with the hosted view, reusing `HostedMap`, `HostedRoomClient` and turn progress. Generate scene-scoped commander invites in the GM panel. A commander joins directly into the battle view of the VTT; the 500 clients neither connect to the GM's peer room nor receive the campaign's documents. Existing campaign players need a seat assignment too; campaign membership alone is not admission.
4. **Keep one writer per battle.** The campaign GM owns the world; the service owns accepted orders, model positions, fog, and turn publication for this battle. [`hostBoot.ts`](../src/app/hostBoot.ts#L1054) currently wires `SimBridge` and `TurnChannel` to `DEFAULT_SCENE_ID`: mounting a hosted panel alone will not disable conflicting local actions. Fence local strategic mutations for the bound scene and participating armies at the host command boundary, not just on buttons. Switching to another scene detaches its view, not the server simulation. On refresh/reconnect, resume the binding; on service loss, keep the last view read-only, never fall back to a second writer. Other campaign scenes remain available.
5. **Finish in the campaign.** End requires an explicit GM action. Attach the published report to the source scene. If unit strengths are to carry forward, apply only agreed fields via one GM-authorized transaction with source-ID mapping, expected campaign revisions and a unique battle/result version. Repeating Finish must not apply casualties twice. Release the local write fence after reconciliation, not merely when the GM leaves the scene.

**Deployment:** start with a web-served VTT and same-origin HTTPS/WSS backend; the pilot already assumes relative API URLs and signs the page origin. Local `file://` campaigns must remain usable offline. Supporting remote 500-seat launch directly from a downloaded HTML is a separate origin/admission design; do not fix it by broadly trusting opaque origins. A separately deployed backend does not imply a separate world file or GM interface.

## Delivery gates

- **Vertical slice first:** from a non-default strategic scene in an open campaign, launch a real room, admit two opposing commanders, submit orders, resolve one turn and see the result on the same canvas. Switch scenes, return, reload and relaunch after an interrupted response: same battle ID and turn. Test rejected launches, membership revocation, and unchanged unrelated scenes. No file dialog, CLI provisioning or second GM page in this flow.
- **Scale separately from UX:** repeat with 100, 250, then 500 commanders plus the GM using realistic clients, TLS/WAN, both 50k-model shapes, and the existing latency/frame/soak/recovery gates. A two-commander vertical slice demonstrates integration, not capacity. Do not advertise 500 until the integrated path passes.
- Fresh checks on the merge: both builds succeeded. Focused Vitest run (`tests/strategicRoom`, `tests/core/turnProgress.test.ts`, `tests/sim/codec.test.ts`, `tests/assets/cache.test.ts`): **40 passed, 4 PostgreSQL tests skipped**. No hosted browser E2E or load qualification was run in this review. PR load measurements and the remaining rollout gates are recorded in the [strategic implementation plan](STRATEGIC_500_IMPLEMENTATION_PLAN.md); 500 commanders is not a qualified capacity.

## Implementation follow-up

The in-scene vertical slice and all three review fixes are implemented on this branch. See the [campaign operator and GM guide](../services/strategic-room/README.md#launch-inside-a-campaign-no-second-world-file) for launch, rejoin, recovery and Finish. The campaign endpoint hosts one active battle at a time; the existing standalone pilot and offline VTT remain available. A published result writes a scene summary, not army HP changes.

Fresh sandbox checks (not reference-host qualification): 74 focused Vitest cases including real PostgreSQL and a generated 500-seat / 50,000-model deployment; typecheck and Svelte compiler gate passed. The built HTML measured 6,149,681 bytes against the 6,291,456-byte budget. Chromium covered offline boot, hosted admission/revocation, 50k compact views and the in-campaign GM + two-commander workflow (both commanders connected for publication). A flaky DevTools response-body capture in the existing 50k browser test was changed to the same route-based capture as its other seats and the hosted batch rerun. Tests used a disposable loopback PostgreSQL, registry-sourced headless Chromium and one worker. No 500-browser WAN or reference-host soak was performed.
