# ArenaStar Macros / FX Wizard — Foundry-module parity specification

**Status:** parity target specification; implementation is in progress and tracked in [`MACROS_FX_WIZARD_IMPLEMENTATION_STATUS.md`](MACROS_FX_WIZARD_IMPLEMENTATION_STATUS.md). This specification is **not** a completion claim. **Research and repository baseline:** 2026-09-23.  **Parity target:** the documented, user-facing capabilities of the ten named Foundry modules/packs below, with extra detail for Sequencer, Tagger, and Monk's Active Tile Triggers (MATT). This is *behavioral and workflow parity*, not a promise that Foundry JavaScript, module ZIPs, proprietary assets, or document schemas run unchanged in ArenaStar. Where a source documents a third-party integration, the relevant integration among these ten is required; integrations with unrelated Foundry modules need an equivalent extension point, not those modules' entire feature sets.

**Release gate:** a Macros / FX Wizard cannot be called parity-complete while it is only a one-action wizard, only procedural particles, only chat macros, or only an FX player without tags, event/action authoring, summons, and prefabs. This parity target **supersedes the narrower FX-scope suggestions** in [`GAP_CLOSURE_ImplementationPlan.md`](GAP_CLOSURE_ImplementationPlan.md) and [`TOOLBAR_PARITY_PLAN.md`](TOOLBAR_PARITY_PLAN.md); it does not retroactively claim those features are built. The dependency order in §11 is an implementation plan, **not** permission to declare an early slice the finished product. Source behavior that is version-specific is described as such; the acceptance tests state ArenaStar's intended behavior, including safety and portability improvements rather than reproducing upstream bugs.

## 3. User-facing wizard and common model

**One product, not ten unconnected panels.** The GM should be able to open *Macros / FX Wizard* from a macro, an actor/item/ability, an active tile/region, a selected token, the FX manager or the asset browser. Each surface edits the **same versioned definition**, with typed references and context inputs. Visual authoring and code authoring compile to the same validated runtime actions; code is a supported power-user path, not a missing feature. A `Sequence` may itself be an action in a trigger graph or a callable macro; a macro may call a sequence, summon or prefab; a tag selector resolves on the host at execution time. [1](https://github.com/fantasycalendar/FoundryVTT-Sequencer/blob/master/docs/api/home.md), [12](https://github.com/ironmonk108/monks-module-wiki/wiki/Tile-Configuration-Window), [23](https://foundryvtt.com/packages/boss-loot-assets-premium).

### 3.1 Canonical authoring objects (suggested schema, not code in this release)

- `SequenceDefinition { id, version, owner, inputSchema, steps[], bindings[], assetRefs[], audiencePolicy }`: typed steps such as `effect`, `sound`, `animation`, `text`, `camera`, `crosshair`, `wait`, `branch`, `repeat`, `invokeMacro`, `invokeSequence`, `summon`, `prefab`, `action`. Each has stable ID, parallel/serial scheduling, optional result references, error policy and documented units. Never overload PF1e `ActiveEffect` or the ping layer to represent a canvas sequence.
- `AutomationDefinition { id, version, anchorRef, zone, triggers[], gates, actions[], stateRef }`: actions may write named variables, filter current selections, branch/land, call subgraphs, return/stop, run code/macro or execute authoritative world ops. Keep authoring graph separate from execution history.
- `TagSelector { tags, match: all|any|exactSet, scene: current|id|all, caseSensitive, wildcard, include, exclude, objectTypes }`: a *data selector*, not a cached list of placeable IDs.
- `FxInstance { id, sceneId, sequenceId, origin, sourceRef?, targetRefs?, audience, startedAt, elapsed, persistent, lifecycleRefs[], state }`; `PrefabDefinition { root, members[], attachments[], rebindingRules[], assets[] }`; `SummonInstance { instanceId, sourceActorRef, summonerRef, tokenRef, control, lifecycle }`.
- A versioned `ActionContext` carries trigger/cast/roll/movement source, selected and current collections, named variables and authorized references. A rendered FX instruction is **not** itself a command to change HP, inventory, movement or permissions.

Implement new collections/embedded fields and migrations in [`documents.ts`](src/core/documents.ts) / world-file validation rather than hiding untyped payloads in unrestricted `flags`. Optional fields must read safely from older worlds; serialized definitions carry a schema version. Reserve `flags` for vendor/compatibility metadata, not a substitute for host validation.

### 5.3 MATT trigger/flow detail to preserve

- **Enter and stop are different events**; a movement can cross more than one zone. Evaluate swept footprint once per committed move, order crossings deterministically and guard double firing if enter+stop or combat start+round+turn coincide. Do not wait for a client animation frame to decide who is in a tile. [11](https://github.com/ironmonk108/monks-module-wiki/wiki/MATT-Trigger-Methods).
- Named **landings** route on method (`_enter`, `_click`, etc.), user, direction, elevation/time where relevant; explicit jump/redirect and success/fail routing also exist. We may choose a less cryptic authoring UI while retaining the behavior. [15](https://github.com/ironmonk108/monks-module-wiki/wiki/MATT-Landing).
- Target collections are distinct: **triggering tokens** (immutable origin) versus **current collection** (changed by filters/rolls). "Tokens within tile" means a spatial query, not a synonym for triggering token. [13](https://github.com/ironmonk108/monks-module-wiki/wiki/MATT-Targeting).
- GM-gated actions are intentional: an automation initiated by a player is **not** an authority to run arbitrary code, edit doors or delete entities. A GM-authored, immutable-to-player macro can explicitly delegate a particular safe invocation. [29](https://foundryvtt.com/packages/advanced-macros), [30](https://github.com/mclemente/fvtt-advanced-macros/blob/main/src/main.js).

## 8. Joined-up authoring scenarios (product demonstrations)

1. **Portable pressure-plate trap (Tagger + MATT + Token Attacher + Sequencer).** GM groups plate tile, door/wall, light, sound emitter and optional concealed token into a prefab; tags `trap-{#}-plate`, `trap-{#}-door` and `trap-{#}-light` are allocated per instance. On a *committed* token-enter event, tile guards check paused state, ownership, per-token history and cooldown. Filter for a PF1e condition; success/fail branches choose an authorized damage/roll action, open the **matching** door by tag, play a sound + masked particle sequence to eligible viewers, and record history. Duplicate prefab twice and trigger one: the other door stays shut; player cannot see or fetch hidden tile tags/assets. [10](https://github.com/fantasycalendar/FoundryVTT-Tagger), [14](https://raw.githubusercontent.com/wiki/ironmonk108/monks-module-wiki/MATT-Actions.md), [17](https://github.com/ironmonk108/monks-module-wiki/wiki/MATT-Use-Tagger), [28](https://github.com/KayelGee/token-attacher).
2. **PF1e ability/cast → cinematic FX → summon.** A single item/cast event supplies token, targets, selected ability, resource/roll resolution and audience. Recognition rule selects a user-owned JB2A/Eskie/other pack variant, prompts crosshair in legal range, preloads eligible players, waits on the committed cast, then starts visual/audio cues and requests transient creature placement. On cancel/failed cast, neither spell resource nor creature state is spuriously duplicated; on dismissal the persistent portal/aura ends with outro. Missing premium art yields a clear dependency notice and a permitted alternative; PF1e mechanics work regardless. [1](https://github.com/fantasycalendar/FoundryVTT-Sequencer/blob/master/docs/api/home.md), [21](https://jules-bens-aa.github.io/jb2a-wiki/getting-started/guides/), [23](https://foundryvtt.com/packages/boss-loot-assets-premium), [24](https://github.com/MrVauxs/foundry-summons-2).
3. **Living scene (FXMaster + tile regions + macros).** GM schedules weather preset at world time/specific darkness, suppresses indoor rain under roof/region, adds sound and scene filter in controllable order, triggers a scripted alert when a party enters a tagged courtyard, pauses scene if authorized and restores the scene state after reconnect. Another sequence can play projectiles **above** the weather but **below** an overhead tile; player fog remains intact. [11](https://github.com/ironmonk108/monks-module-wiki/wiki/MATT-Trigger-Methods), [27](https://github.com/gambit07/fxmaster/blob/main/README.md).
4. **Macro-to-world automation.** A GM script queries all tagged `guardian*` tokens on one scene, filters owner/visibility, animates two parallel attacks, awaits PF1e host rolls, applies only authorized results, then calls a tile graph by reference. The player may invoke a granted macro with typed target arguments but cannot change its implementation or redirect it to a secret scene. [10](https://github.com/fantasycalendar/FoundryVTT-Tagger), [29](https://foundryvtt.com/packages/advanced-macros), [33](https://github.com/ironmonk108/monks-module-wiki/wiki/MATT-Run-Macro).

These scenarios are **acceptance demonstrations**, not a hardcoded spell/trap list. The wizard must create and edit equivalent flows from user-defined assets and modules.

### 9.1 Non-negotiable authority, privacy and resilience requirements

| ID | Requirement | Acceptance |
| --- | --- | --- |
| SC-01 | Host validates every trigger, summon, macro, document op and audience request against caller, published definition/revision, selected targets and system rules; visual-only client messages cannot authorize mechanics. | A05, A20, A35–A36 |
| SC-02 | Project sequences, persistent instances, trigger history, tag query results, live managers, debug output, chat, sound and screen-space effects per viewer, **including reconnect replay**; fog/LOS and hidden source documents are enforced even after source moves or changes visibility. | A07, A11, A23, A35–A39 |
| SC-03 | Project asset *metadata* and authorize individual asset chunk requests for the intended viewer; an authenticated but unentitled session cannot enumerate or download hidden/premium art through the manifest, a guessed hash or an external URL. Licenses govern distribution separately. | A30–A31, A35 |
| SC-04 | GM-elevated macros/inline code are authored and approved by a GM, immutable to player edits, version-pinned and audited; recipient/all-user execution never multiplies host world mutations. | A34–A37 |
| SC-05 | Host-issued correlation/event IDs, transaction state and idempotency prevent duplicate damage, triggers, summons and rewards on retries, overlapping methods, scene reload and reconnect. | A20–A21, A38–A40 |
| SC-06 | Validate typed selectors and programmatic inputs; bound regex/recursion/resources; escape interpolated chat/HTML, review URLs and package media, and prevent script RPC from escaping capability boundaries. | A13, A26–A27, A35–A37 |
| SC-07 | Delayed/persistent effects and trigger state resume from authoritative state; canceled/failed world actions clean up provisional media/attachments and surface diagnostics without pretending the action succeeded. | A03, A17–A18, A39–A40 |

**Execution ordering:** (1) host accepts a movement/cast/roll/permissioned request; (2) authoritative state and trigger state commit once; (3) host chooses recipient-specific effect/feedback instructions and asset entitlements; (4) recipient clients schedule media on a host-clock timestamp and render locally. A local preview bypasses (1)–(3) **only in a nonmutating test context**. Visual catch-up on reconnect cannot re-run mechanical actions. A trigger that is denied or aborted cannot still deal damage or play secret FX.

**Privileged scripting model:** two execution contexts are valid: (a) user/creator scripts with capability-limited API and caller authority; (b) GM-installed scripts with explicit GM trust, version pin, reviewer-visible code, audit and narrowly granted invocation for players. A player may invoke a published GM script but cannot edit it or supply undocumented arbitrary ops. `runAsEveryone` means recipient-side rendering where appropriate; world mutation stays singular on host. This is **not** a blanket prohibition on JS or a restriction to declarative single actions.

**Privacy invariants:** only show FX/audio/manager entries if their source, target, effect and referenced asset are authorized for that viewer; a GM-only trap graphic or tag must not reveal a hidden entity. By default world effects respect fog/LOS; an explicit theatrical overlay is allowed only to viewers authorized for its originating event. Add per-user asset entitlement/projection to both snapshots *and* chunk requests. Defense in depth: do not assume that hiding a Pixi sprite hides its socket payload, asset hash/name, or sound.

**Performance and resilience:** avoid per-frame network replication, retain saved origin and start time, throttle/cull offscreen effects per client, preload by lead time, adapt density to local settings, terminate runaway *cycles* rather than rejecting legitimate long graphs. Verify actual browsers/codecs (especially transparency) and fall back explicitly; never silently alter mechanical outcomes. Backups/export must round-trip published definitions, selected pack dependencies, tag rebinding and persistent instances.

## 11. Delivery sequence and final definition of done

Dependencies can be built in increments without redefining the user's parity goal:

1. **Shared foundation:** versioned documents/migrations, event/outcome contracts, tag index/query API, asset entitlement model and permissioned host action registry. Implement the complete tag semantics and wire/privacy tests first because all other flows depend on them.
2. **Playback platform:** media registry/browser, sequence scheduler and Pixi/audio strata, crosshairs, effect/sound managers, persistence and recipient-safe network transport. Ship rich timeline **and** programmable API as interfaces to the same scheduler; do not stop at procedural particles.
3. **Automation + prefab:** tile/region geometry, all trigger methods/gates, selectors, all §5.4 core action/filter/flow contracts, tag/prefab rebinding and full editor/debugger. Make generic action registration available for future systems/modules.
4. **Complete cross-module workflows:** PF1e item/cast bindings + recognition, summons, FXMaster-style environment, multi-layer Token Attacher-style prefabs, advanced macros and code/trust modes. Confirm all four §8 flows end-to-end.
5. **Parity exit:** all §2 crosswalk rows and §10 tests, **per-action inventory fixtures**, browser/server performance/visibility security, lawful asset handling, export/reconnect migration and creator docs. If an individual capability is unavailable, mark it as an explicit **parity gap** in a tracking matrix rather than changing the definition of the Wizard.

**Acceptance statement:** a GM can author, share and debug a tagged multi-object active trap, a timed audiovisual PF1e ability with optional paid-but-user-provided animations, a weather/region scene, a summoned actor and a player-invoked GM-approved advanced macro **using one integrated wizard**; the right peers see/hear only what they may know; world mechanics remain authoritative and exactly-once; no unlicensed premium media ships with ArenaStar.
